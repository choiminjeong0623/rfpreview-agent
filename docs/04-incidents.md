## 1. Docker에서 "AI 끄기" 설정이 무시됨

- **증상.** `.env`에 `RFP_AI_MODE=off`를 넣고 Docker Compose로 띄웠는데도, 분석하면 Gemini로 요청이 나갔습니다.
- **원인.** Docker Compose는 `docker-compose.yml`의 `environment`에 적힌 변수만 컨테이너에 넘깁니다. `RFP_AI_MODE`와 `GEMINI_MODEL`이 그 목록에 없어서, 백엔드는 기본값(`gemini`)으로 동작했습니다. `uv run uvicorn`으로 직접 띄울 때는 `.env`를 읽어 문제가 드러나지 않았습니다.
- **조치.** `docker-compose.yml`과 `.env.example`에 변수를 더하고, 키가 있는 상태에서 `RFP_AI_MODE=off`로 `docker compose up -d backend`를 실행해 `/api/health`가 `"ai_mode":"OFF"`인 것을 확인했습니다(11-02).
- **재발 방지.** "새 설정 변수는 `config.py`, `.env.example`, `docker-compose.yml` 세 곳을 함께 고친다"를 AI 에이전트 작업 지침(`CLAUDE.md` "자주 걸리는 것")에 넣었습니다. 지금 방식과 외부 전송 여부를 `/api/health`와 실행 기록 화면에 항상 보이게 했습니다.
- **교훈.** 보안 설정은 "켰다"가 아니라 **실제로 적용됐는지 확인할 수 있는 화면**이 있어야 합니다.

## 2. 실제 RFP 1건 처리에 15분 넘게 걸림

- **증상.** 실제 입찰 서식 문서로 처음 로컬 테스트를 했을 때(10-29) 처리에 약 15분이 걸렸고, AI 응답이 오지 않으면 "멈춤 안내"만 뜨고 재시도·실패로 넘어가지 못할 수 있었습니다.
- **원인.** 실행 기록을 보니 시간 대부분이 문서 읽기 단계의 AI 일(문장 구분·유형)이었습니다. 40줄 묶음을 **하나씩 차례로** 묻고 있었고, AI 요청에 시간 제한이 없었습니다.
- **조치.** 묶음을 정해진 개수(기본 4, `RFP_LLM_WORKERS`)만큼 동시에 묻고 **답은 순서대로** 받게 했습니다. 요청마다 시간 제한(기본 120초)을 두었습니다(`update-llm-concurrency`). 문서가 여러 개면 문서끼리도 동시에 처리합니다(`add-document-processors`, 기본 2).
- **결과.** 같은 문서 6.3분(이후 측정 6분 16초). 문서 2개 묶음(AI 끔) 87.1초 → 64.4초. 워커 수와 상관없이 요구사항·판정 수가 같은 것을 확인했습니다(재현성 CR-11).
- **한계.** "15분"은 잰 값이 아니라 기록된 관찰이고, 그 사이 코드 판도 달라 엄밀한 전후 비교는 아닙니다. 팀 기간에는 작업 대기열을 다음 단계로 남겼고, 수료 뒤 PostgreSQL 작업 대기열과 처리기로 만들었습니다([07 트러블슈팅 5-1](07-troubleshooting.md#5-1-큰-스캔-pdf를-올리면-등록-응답이-몇-분-걸림), `add-run-queue`).

## 3. 비교 제품 칸 응답이 17초

- **증상.** 실제 입찰 서식 검토(설비 묶음 238개, 값 4,929개)의 검토 상세 화면에서 비교 제품 칸이 17.1초 걸려 떴습니다.
- **원인.** 요구값 테이블의 `requirement_id`와 표 행의 `parent_row_id`에 색인이 없어, 값마다 표 전체를 훑었습니다. 같은 질의를 판정 단계도 쓰고 있었습니다.
- **조치.** 마이그레이션으로 색인 두 개를 더했습니다(0035).
- **결과.** 17.1초 → **0.87초**.
- **교훈.** 합성 문서(수십 줄)로만 테스트하면 드러나지 않습니다. 실제 크기 문서로 한 번은 돌려 봐야 합니다.

## 4. 같은 파일을 거의 동시에 올리면 문서 읽기에서 멈춤

- **증상.** 로컬 E2E를 작업자 2개로 돌리자, 검토 하나가 "문서 읽기"에서 멈추고 자동 재시도도 같은 오류로 실패했습니다. 홈 알림에 DB 오류 원문이 보였습니다(10-31 재현).
- **원인.** 내용이 같은 파일은 처리 결과를 다시 쓰도록 만들어 두었는데(`update-document-reuse`), 두 검토가 동시에 "아직 처리한 문서 없음"을 보고 둘 다 처리를 시작했습니다. 늦게 저장하는 쪽이 문서 고유 키 충돌로 실패했습니다. 전형적인 "확인 후 실행" 경쟁 상태(race condition)입니다.
- **조치.** 저장이 겹치면 오류로 멈추지 않고 **먼저 저장된 결과를 다시 쓰도록** 했습니다(`update-document-reuse-race`).
- **교훈.** 실제로는 같은 RFP를 두 사람이 거의 동시에 올릴 때 생기는 일입니다. 동시 실행 테스트를 E2E에 남겼습니다.

## 5. AI 오류를 모두 같은 방식으로 재시도

- **증상.** 어떤 AI 오류든 같은 질문을 2번 더 물었습니다. 키가 틀렸을 때도 3번 묻고 "처리 실패 — 다시 시도"를 띄워 사람이 다시 누르게 했고, 위험 설명 하나의 형식이 틀리면 검토 전체가 실패했습니다.
- **원인.** 오류 종류를 나누지 않았습니다. temperature 0이라 형식 오류는 다시 물어도 같은 답이 나오기 쉽습니다.
- **조치.** 오류를 셋으로 나눴습니다(`update-llm-retry-kinds`).
  1. 연결·시간 초과·서버 오류·요청 많음(429): 지금처럼 2번 더 묻습니다.
  2. 형식 오류: 다시 묻지 않습니다. 묶음 질문은 바로 반으로 나눠 묻고, 위험 설명은 버리고 이유(FORMAT_ERROR)를 남기고, 문장 초안은 그 줄만 코드 기본 문장으로 바꿉니다. **검토는 멈추지 않습니다.**
  3. 키·권한·모델 설정 오류: 다시 묻지 않고 "AI 키 또는 모델 설정 오류 — 설정 확인"으로 바로 멈춥니다.
- **결과.** 버린 설명과 이유가 실행 기록에 건수로 남아, AI 품질 문제를 숫자로 볼 수 있게 됐습니다.

## 6. AI가 견적 관련 문장을 요구사항에서 빼 버림

- **증상.** 시연용 합성 RFP를 AI를 켜고 분석하자 견적 협조 요청이 3건에서 2건으로 줄었습니다. AI를 끄면 3건이었습니다(11-02).
- **원인.** AI 문장 구분이 "입찰 가격에 통화·유효 기간·지급 조건을 적어야 한다"는 문장을 "작성 규칙"(요구사항 아님)으로 옮겼습니다. 요구사항에서 빠지자 "비용 영향" 유형도 붙지 않아 견적 부서로 가지 않았습니다. 위험 표현 문장은 이미 같은 이유로 AI에 묻지 않게 보호하고 있었지만, 부서 협조 요청 유형에는 같은 보호가 없었습니다.
- **조치.** 협조 요청이 생기는 유형(비용 영향·시험·제조사 자격) 규칙에 걸리는 문장은 **AI에 묻지 않고 요구사항으로 둡니다**(`update-ai-label-keep-handoff`). 코드가 정합니다(CR-01).
- **교훈.** AI가 "빼는" 결정도 업무에 영향을 줍니다. 놓치면 안 되는 문장은 규칙으로 지키고, AI는 나머지만 판단하게 했습니다. 같은 측정에서 AI 켬은 요구사항 정확도가 오르고(94.0 → 100 %) 재현율이 내려가는(72.3 → 63.1 %) 경향이 있어, 재현율 쪽은 코드 규칙으로 보완했습니다(`update-extract-recall`).

## 7. 테스트는 통과하는데 실제 제품표로는 판정이 안 됨

- **증상.** 실제 제품표를 넣고 분석하자 "정격 전류 3150 A 이상" 같은 요구가 모두 "확인 필요 — 제품값 없음"이 됐습니다. 테스트는 모두 통과하고 있었습니다.
- **원인.** 실제 제품표의 GIS 4종에 정격 전류와 단시간 전류 시간이 비어 있었습니다. 테스트는 **고정 제품표 픽스처**만 써서, 실제 제품표가 비어도 통과했습니다.
- **조치.** 카탈로그 쪽수와 함께 값을 채우고(팀 가정이 아닌 실제 값), **실제 제품표를 적재해 값·판정을 확인하는 테스트**를 더했습니다(`update-gis-catalog-values`).
- **교훈.** 픽스처 테스트와 함께, 실제 기준 데이터로 도는 테스트가 하나는 있어야 합니다.

## 8. AI가 만든 정답으로 AI를 채점해 결론이 뒤집힘

- **증상.** 두 모델(3.8 Flash와 Lite)이 요구사항 판단이 갈린 18줄을 Claude가 만든 정답으로 채점하면 3.8이 13줄, Lite가 3줄 맞혀 3.8이 크게 앞섰습니다. 그런데 사람 2명이 다시 확인해 합의한 10줄 기준으로는 **3.8이 0줄, Lite가 10줄**이었습니다.
- **원인.** 정답을 만든 AI와 채점받는 AI의 기준이 비슷했고, "요구사항"의 정의(서식 작성 안내를 요구사항으로 볼지)가 사람과 시스템 사이에 달랐습니다. 결국 모델 차이가 아니라 **정의 차이**를 재고 있었습니다.
- **조치.** 이 비교를 모델 선택 근거에서 뺐습니다. 모델 선택 근거는 사람 확인 결과(유형 22줄)와 코드 검사(문장 초안, 판정 건수)로만 둡니다. 정답지마다 만든 이(사람 / 코드 / Claude 초안)를 기록하고, Claude 초안은 "사람 확인 전"으로 표시합니다.
- **교훈.** 평가 데이터의 출처를 숫자와 함께 적어야 합니다. 이 내용은 [05 평가 결과](05-evaluation.md)의 모든 표에 반영했습니다.

## 9. 고객 RFP 문장이 든 실험 파일이 커밋됨

- **증상.** 모델 비교 실험 결과 CSV 3개(고객 RFP 문장과 설비 위치가 든 정답지·결과)가 커밋됐습니다(11-02).
- **원인.** `data/private/`는 처음부터 git에서 막았지만, 실험 폴더(`experiments/`)의 결과 파일은 막지 않았습니다.
- **조치.** 다음 커밋에서 지우고 `.gitignore`에 넣었습니다. 팀 저장소는 비공개로 유지했습니다. 이 공개 사본은 그 이력을 가져오지 않고 **첫 커밋 하나로 새로 시작**했습니다.
- **교훈.** 파일을 지워도 git 이력에는 남습니다. 비밀 데이터는 "폴더"가 아니라 "내용" 기준으로 막아야 하고, 공개 전에는 이력 전체를 검사해야 합니다. 이 공개본을 만들 때 이력 전체에서 `.env`, API 키 패턴, 고객 문서 경로를 검사했습니다([data.md](data.md)).
