## 6. 이 프로젝트에서 배운 것

1. **AI에게 무엇을 맡기지 않을지 먼저 정하는 것**이 설계의 핵심이었습니다. "숫자·판정·분기는 코드만"이라는 규칙 하나가 재현성, 근거 추적, AI를 끄고도 도는 구조, 모델 교체 실험을 모두 가능하게 했습니다.
2. **평가 데이터의 출처를 숫자와 함께 적어야** 합니다. AI가 만든 정답으로 채점하다 결론이 뒤집힌 경험 뒤, 모든 지표에 "정답을 정한 이"를 붙였습니다.
3. 4명이 AI 코딩 에이전트와 동시에 개발할 때는 **스펙과 추적표가 팀의 공통 언어**가 됩니다. 무엇을 했고 무엇을 못 했는지가 표로 드러나, 발표에서도 한계를 정직하게 말할 수 있었습니다.
4. 실제 크기 데이터로 한 번은 끝까지 돌려 봐야 합니다. 성능(17초 → 0.87초)과 제품표 빈칸 문제는 합성 데이터 테스트로는 드러나지 않았습니다.

### 내가 내린 설계 판단 3가지

| 판단 | 정한 것 | 이유 | 버린 것 · 결과 |
|---|---|---|---|
| AI는 판정하지 않음 | 숫자 계산·판정·다음 단계 고르기는 코드만, AI는 문장 읽기·쓰기만. 문장 속 숫자는 자리표시자로 받고 코드가 채운 뒤 근거와 대조 | 입찰 검토 결과는 계약 조건이 됨. 실행마다 판정이 바뀌거나 AI가 빈칸에 그럴듯한 값을 채우면 그대로 위험 | LLM이 값을 읽고 판정까지 하는 방식을 버림. AI를 꺼도 판정이 같고 보증값 지어냄 0건. 대신 "확인 필요"가 많이 남음 ([ADR-002](03-adr.md#adr-002-숫자판정분기는-코드만-ai는-문장만)) |
| K5를 99 % → 88 %로 고쳐 적음 | 실제로 판정을 낸 줄(일탈 6·질의 5·준수 6)만 세어 15/17 = 88 % | 채점 화면의 99/100 중 77건은 확정하면 다음으로 넘어가며 확정된 "확인 필요" 줄이라 정확도를 부풀림 | 좋아 보이는 숫자를 그대로 쓰는 것을 버림. 설명할 수 없는 숫자는 쓰지 않음 ([05 평가](05-evaluation.md)) |
| 프롬프트 회귀를 문항 단위로 셈 | 회귀를 %p가 아니라 "다 맞지 못한 문항이 몇 개 늘었나"로 판단 | 프롬프트를 그대로 둬도 모델이 흔들려 회귀가 나옴. 3번 반복·최솟값 비교로도 8문항 도우미는 한 문항에 12.5 %p가 빠짐 | 한 번 잰 기준선과 %p 문턱을 버림. 같은 흔들림의 거짓 회귀 2건 → 0건, 유형 정의를 뒤섞은 PR #25는 90.0 → 76.7 %로 CI가 막음 ([ADR-009](03-adr.md#adr-009-프롬프트-평가를-직접-만듦)) |

## 7. 수료 뒤 혼자 더한 것 (11-14 ~ 11-16)

팀 프로젝트(11-10 종료) 뒤 이 공개 사본에서 혼자 한 작업입니다. PR #1 ~ #22, 변경 제안 17건, 마이그레이션 0040 ~ 0046이며 커밋 이력이 그대로 남아 있습니다. 시작은 멘토 질문 "프롬프팅에 따라 품질을 측정하는 부분이 있는가"였고, 명세서에 FR-18 ~ 23을 먼저 적고 하나씩 구현했습니다. 강점별 자세한 근거는 [아래 표](#강점별-근거)에 있습니다.

**Claude Code를 쓴 방식.** 이 작업의 코드는 대부분 Claude Code가 썼고, 커밋에 공동 작성자로 남아 있습니다. 저는 무엇을 만들지와 맞는지를 정했습니다. 명세서에 요구사항을 먼저 적고, Claude가 쓴 변경 제안을 제가 확인한 뒤에만 구현을 시작했습니다. "AI는 판정하지 않는다" 같은 규칙은 `AGENTS.md`·`CLAUDE.md`에 적어 사람과 AI가 같이 따르게 했고, 결과는 테스트·CI·정답지 채점으로 확인했습니다. 부풀려진 숫자는 받아들이지 않고 다시 셌습니다(K5 99 % → 88 %).
