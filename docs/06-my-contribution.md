## 4. 내세우기 · 입찰 연결 — 판정 결과를 입찰 무기로

"지키기"만으로는 일반 AI와 차이가 없다는 현업 의견을 받아, 판정 결과를 **고객에게 내세울 근거**와 **입찰 서류**로 잇는 부분을 맡았습니다.

| 기능 | 하는 일 | 지킨 원칙 |
|---|---|---|
| 기술 제안 포인트 (FR-14) | 판정의 여유(예: 단시간 전류 요구 1초 ↔ 제품 3초), 손실 환산 우위, 현장 이력에서 후보를 코드가 고르고 AI는 문장만 씀. 엔지니어가 채택 / 버림 / 수정, 채택분만 영업·견적에 전달 | 근거 칸(요구 원문 위치, 제품 행)이 비면 후보를 만들지 않음 → **근거 없는 제안 0건(K12)** |
| 손실 환산 (FR-13) | RFP의 "변압기 손실 1 kW당 금액을 입찰가에 더한다" 조항을 찾아 단가 × 손실값을 계산. 같은 조건의 단가 표는 묶어 보임 | 계산은 코드만, 손실값은 "팀 가정" 표시, 다시 계산해 대조(K8) |
| 현장 이력 연결 (FR-15) | 요구 항목(예: 결로 방지 히터) ↔ 우리 제품군 고장 사전·해결 사례 연결 | 팀이 확정한 연결표에 있을 때만 연결, AI가 즉석에서 짝짓지 않음. 제품군 단위 연결만 주장 |
| 입찰 서류 내보내기 | TBE 준수표·데이터시트 엑셀, 결재 승인 뒤 **영업 인계 패키지**(일탈·질의 Word, TBE·데이터시트 엑셀 zip)와 미리 보기 | 결재 전에는 인계하지 않음, 금액 칸은 비움 |

관련 변경 제안: `add-judgment-and-outputs`(FR-13·14 부분), `add-field-history`, `update-proposal-actions`, `add-tbe-export`, `add-datasheet-export`, `add-cost-conditions`, `add-submission-package`, `update-loss-tab-group`, `update-package-progress`, `add-package-preview`

## 6. 이 프로젝트에서 배운 것

1. **AI에게 무엇을 맡기지 않을지 먼저 정하는 것**이 설계의 핵심이었습니다. "숫자·판정·분기는 코드만"이라는 규칙 하나가 재현성, 근거 추적, AI를 끄고도 도는 구조, 모델 교체 실험을 모두 가능하게 했습니다.
2. **평가 데이터의 출처를 숫자와 함께 적어야** 합니다. AI가 만든 정답으로 채점하다 결론이 뒤집힌 경험 뒤, 모든 지표에 "정답을 정한 이"를 붙였습니다.
3. 4명이 AI 코딩 에이전트와 동시에 개발할 때는 **스펙과 추적표가 팀의 공통 언어**가 됩니다. 무엇을 했고 무엇을 못 했는지가 표로 드러나, 발표에서도 한계를 정직하게 말할 수 있었습니다.
4. 실제 크기 데이터로 한 번은 끝까지 돌려 봐야 합니다. 성능(17초 → 0.87초)과 제품표 빈칸 문제는 합성 데이터 테스트로는 드러나지 않았습니다.
