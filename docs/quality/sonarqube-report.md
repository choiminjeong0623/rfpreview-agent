## 2. 발견한 구조 문제: 목업 CSS가 운영 스타일로 쓰이던 구조

### 무엇이었나

화면 CSS 31개가 `frontend/src/mockup/` 폴더에 있었다. 이름은 "목업(시안)"이지만 실제 앱의 스타일이다.

- `Main.css`는 `main.tsx`에서, `SummaryV496.css`는 `SummaryBox.tsx`에서 늘 불러온다.
- 나머지는 `shell/pageCss.ts`의 `import.meta.glob`과 화면마다 `usePageCss('키')`로, 그 화면이 보이는 동안에만 `<style>`로 붙였다가 뗀다.

폴더 이름 때문에 사람도 분석 도구도 "쓰이지 않는 시안"으로 오해하기 쉬웠다. 분석 대상에서 빼면 점수는 오르지만, 실제로 쓰는 코드를 감추는 일이라 빼지 않았다.

### 왜 그렇게 만들었나

`pageCss.ts`와 `usePageCss`는 원래 팀 저장소의 커밋 `b41e3ea` "목업 v4.57 화면 24개 구현 (#16)"(2026-10-29)에서 처음 생겼다. 공개 저장소에는 첫 업로드 커밋 하나로 합쳐져 있어 이 이력이 보이지 않는다. 당시 설계 문서(`openspec/changes/archive/2026-10-28-update-app-shell/design.md`)와 `docs/screens/_디자인.md` 1장의 이유는 이렇다.

1. 목업과 픽셀까지 같게 맞추려고 목업 CSS를 **고치지 않고 그대로** 옮겼다. "색 토큰만 뽑아 CSS를 새로 쓰기"는 목업과 맞추기 어렵고, 목업 새 판이 나올 때마다 다시 옮겨야 해서 버렸다.
2. 목업은 화면마다 CSS 전체를 따로 갖고 있고 `.tbl`·`.card` 같은 클래스 이름이 겹친다. 그래서 한꺼번에 불러오지 않고 보이는 화면의 CSS만 붙였다.
3. 새 목업 판이 오면 파일을 통째로 바꿔 끼우려는 목적이었다.
4. 쓰지 않는 규칙도 함께 실리는 것(약 33 KB)은 알고 받아들인 위험이었다.

### 이번에 바꾼 것

- 폴더 이름을 `frontend/src/mockup/` → `frontend/src/styles/pages/`로 바꿨다. CSS 내용은 한 글자도 바꾸지 않았다.
- `pageCss.ts`의 glob에서 `Main.css`와 `SummaryV496.css`를 뺐다. 이 둘은 정적 import로 이미 CSS 묶음에 들어가는데, glob이 같은 파일을 JS 조각(30.6 KB, 2.4 KB)으로 한 번 더 만들고 있었다. 이 조각은 어디서도 불리지 않았다.
- 경로를 쓰던 곳(`main.tsx`, `SummaryBox.tsx`, `pageCss.ts`, 색 검사 스크립트 `check-tokens.mjs`의 제외 경로, 주석, 화면 문서)을 함께 고쳤다.

- **Notice.css와 SysNotice.css 합치기**: 첫 줄 주석만 다르고 내용이 같다.
- **CSS 구조 다시 쓰기**: 목업 CSS를 화면마다 통째로 싣는 대신 CSS Modules 등으로 옮겨, 클래스 이름 겹침과 쓰이지 않는 규칙을 없앤다.
- **메인 JS 용량 줄이기**: `index-*.js`가 약 899 KB로 권장 크기(500 KB)를 넘는다. 화면별 코드 분할(동적 import)로 줄인다.
- **ACCEPT_FOLLOWUP 19건**: 4장 표의 항목. 특히 백엔드 정규식 9건은 실제 RFP 문서로 결과가 같은지 확인하는 시험을 먼저 만든 뒤 고친다.
- **Dockerfile 실행 사용자**: 컨테이너를 root가 아닌 사용자로 돌린다(볼륨 권한 정리와 함께).
- **분석 경고 2건**: SonarCloud 화면에 "2 analysis warnings"가 표시되어 있다. 내용은 로그인해야 보인다.
