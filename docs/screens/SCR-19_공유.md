# SCR-19 정답지·채점: 목업과 다르게 만든 것 (공유)

11-01 `add-evaluation`으로 실제 화면이 됐다. 예시 띠·예시 데이터(`examples/SCR-19.ts`)는 지웠다.

| # | 목업 | 앱 | 이유 |
|---|---|---|---|
| 1 | 지표 K1~K12 (목업 번호: K3 원문 위치, K4 판정 일치율 …) | **기획서 2-2 번호**(K4 원문 위치, K5 판정 정확도, K6 일탈 재현율, K11 지어낸 값, K12 근거 없는 제안, K13 유형 분류) + 처리 시간 | 발표·문서와 같은 번호를 써야 한다. 목업 번호는 기획서와 달랐다 |
| 2 | 지표 12개 모두 값 있음 | 요구사항 정답지가 있어야 하는 K1·K2·K3·K8·K9·K10은 "재지 않음" | 요구사항 정답지(사람이 원문에서 요구사항을 표시한 것)가 아직 없다. 지어내지 않는다(CR-04) |
| 3 | 정답지 = 사람이 확정한 검토 목록 | 같음 + 유형 정답지 고르기, "Claude 초안 · 사람 확인 전" 꼬리표 | 11-01 결정: Claude 초안 100줄을 사람 확인 전으로 표시해 쓴다 |
| 4 | 개선 기록 "고친 곳" 칸 | "정답지" 칸(고른 유형 정답지), "무엇을 고쳤나"는 채점 때 쓴 메모 | 무엇을 고쳤는지는 사람이 적는다. 점수 칸은 K5 · K13 |
| 5 | "지금 채점하기" 1.6초 뒤 0.4 오름 | 실제로 채점하고 기록 | 실제 화면 |
| 6 | 정답지 넣기(목업에 없음) | 명령 `rfp-db load-answer-key` | 파일 올리기 화면이 더 필요해 명령으로 충분하다고 봄 |
| 7 | 쪽 나눔 모양(목업 공통 pgx) | 앱 공통 쪽 나눔(10·20·50개씩) | 다른 화면과 같은 부품 |

## 팀에 알릴 것

- K5·K6는 엔지니어가 확정·수정한 줄만 정답으로 본다. 수정한 줄의 시스템 판정은 첫 수정 이력의 이전 값. 확정한 줄이 적으면 점수가 흔들리니 분자·분모를 같이 본다.
- K13은 정답지 원문과 **글자가 같은**(공백·대소문자 무시) 요구사항만 맞춘다. 원본 RFP를 분석한 DB에서 채점해야 줄을 찾는다.
- 유형 정답지 원본(고객 원문 포함)은 커밋하지 않는다. `data/private/`에 두고 명령으로 넣는다.
