# 화면 공통 규칙

모든 SCR 명세는 이 문서를 따른다. 화면 명세에는 이 문서와 다른 점만 적는다.

## 1. 화면 상태 4종

| 상태 | 언제 | 보이는 것 | 지금 코드 |
|---|---|---|---|
| 로딩 중 | 첫 응답 전 | 표·카드 자리에 회색 줄(스켈레톤). 머리글과 탭은 먼저 보인다 | `useLoad`의 `data === null && error === null` |
| 데이터 없음 | 응답이 빈 배열 | 영역 안에 한 줄 안내. 화면마다 문구를 정한다(예: "위험 조건 후보가 없습니다") | 화면마다 |
| 오류 | API가 4xx·5xx | 영역 안에 오류 문장 + "다시 불러오기" 버튼. 문장은 API의 `detail`을 그대로 쓰고, 없으면 "API {상태 코드}" | `ErrorText`, `useLoad.reload` |
| 권한 없음 | 고른 사용자의 역할로 할 수 없는 동작 | 버튼을 숨기지 않고 비활성화 + 이유 툴팁(예: "승인자만 결정할 수 있습니다") | 화면마다 |

- 동작 버튼은 누르는 동안 비활성화하고, 성공하면 그 영역만 다시 불러온다.
- 동작이 실패하면 화면 값을 바꾸지 않고(낙관적 갱신 안 함) 버튼 옆에 오류 문장을 보여 준다.
- 단계 때문에 못 하는 동작(API 409, 예: 승인 대기 중 판정 고치기)은 권한 없음과 같은 모양으로 비활성화하고 이유를 보여 준다.
- 처리 중(`PROCESSING`) 실행은 2초마다 실행 요약을 다시 부른다(지금 `App.tsx`와 같음). 다른 상태는 자동으로 다시 부르지 않는다.

## 2. 값 종류와 라벨 (API 기준, 2026-10-28 결정)

값 종류(선택지 목록)는 API를 따르고, 화면에는 아래 라벨만 쓴다. 목업에만 있는 선택지는 쓰지 않는다.
라벨의 출처는 `frontend/src/components/labels.ts` 하나이며, 새 라벨은 거기에 더한다.

| 칸 | API 값 → 화면 라벨 | 목업과 다른 점 |
|---|---|---|
| 판정 결과 | `COMPLY` 준수 · `DEVIATION_CANDIDATE` 일탈 후보 · `QUERY_CANDIDATE` 질의 후보 · `NEEDS_REVIEW` 확인 필요 · `WARRANTY_TO_FILL` 보증값 작성 | 목업 "작성 필요" → "보증값 작성" |
| TBE 준수 여부 (영문) | `COMPLY` Comply · `DEVIATION_CANDIDATE` Deviation · `QUERY_CANDIDATE` Clarification · `NEEDS_REVIEW` To be confirmed · `WARRANTY_TO_FILL` To be filled | 목업에 없는 To be filled 추가 |
| 실행 단계 | `PROCESSING` 처리 중 · `ENGINEER_REVIEW` 담당자 확인 · `APPROVAL` 승인 대기 · `APPROVED` 승인됨 · `REJECTED` 반려됨 · `FAILED` 처리 실패 | 목업의 "협조 대기", "제출 준비"는 단계가 아님. 홈 칸반의 "협조 대기"는 끝나지 않은 할 일이 있는 담당자 확인 실행으로 계산 |
| 문서 종류 | `BID_FORM` 입찰 양식 · `REQUIREMENT_SPEC` 요구 사양서 · `PURCHASE_SPEC` 구매 사양서 · `TEST_SPEC` 시험 사양서 · `SUPPLIER_SPEC` 공급사 사양 · `BOQ` 물량표 · `UNKNOWN` 종류 모름 | 목업 8종(입찰 안내서·가격표 등) 대신 이 7종 (물량표: add-boq-processor) |
| 요구사항 유형 | `TECH_PERF` 기술 성능 · `STANDARD_CERT` 적용 규격·인증 · `SITE_ENV` 설치 환경 · `MAKER_QUAL` 제조사 자격 · `TEST` 시험 · `COST` 비용 영향 · `RISK` 위험 조건 (`TYPE_NAMES`) | 목업의 운송·포장, 보증·서비스는 빼고 비용 영향, 위험 조건을 넣음 |
| 할 일 상태 | `TODO` 할 일 · `DOING` 하는 중 · `DONE` 끝 | 목업의 미확인·확인 대신 3단계. "24시간 넘게 미확인"은 `TODO`이고 `sent_at`이 24시간 지난 것 |
| 위험 조건 종류 | `BLANKET` 포괄 조항 · `VALUE_MISMATCH` 값 불일치 · `OPEN_SCOPE` 범위 모호 · `COST_SHIFT` 비용 전가 | 비용 전가는 위험 표현 사전의 종류이고, 찾은 후보는 포괄 조항으로 묶여 보인다 |
| 후보 상태 | `CANDIDATE` 후보 · `CONFIRMED` 확정 · `EDITED` 수정함 · `EMPTY_REVIEW` 확인 필요 · `DRAFT` 초안 · `REMOVED` 뺌 · `ADOPTED` 채택 · `DISCARDED` 버림 · `CLOSED_OK` 문제 없음 | 목업 "후보확정"처럼 두 상태를 겹쳐 쓰지 않음 |
| 사용자 역할 | `ENGINEER` 기술 검토 엔지니어 · `APPROVER` 승인자 · `COST` 견적 담당 · `QUALITY` 품질 담당 · `SALES` 영업 담당 | 직급(대리·책임)은 없음 |

## 3. 표시 형식

| 대상 | 형식 | 예 |
|---|---|---|
| 검토 번호 | `RV-<시작 연도>-<실행 번호 세 자리>` (`add-review-info` 이후 API가 줌) | RV-2026-025 |
| 날짜·시각 | 올해는 `MM-DD HH:mm`, 다른 해는 `YYYY-MM-DD` | 10-24 15:30 |
| 마감 | 목업처럼 `D-n`, 오늘은 `D-Day`, 지나면 `D+n`. 3일 이하 빨강, 7일 이하 주황. 아래 줄에 날짜 | D-6 10-30 |
| 상신 권장일 | 제출 마감 2일 전(달력 기준), 화면 코드가 `due_date`로 계산. 마감이 없으면 비움. 지났으면 빨강 (`_v4.96_결정.md` Q3) | 10-28 |
| 순번 | 모든 목록 표 맨 왼쪽. 쪽을 넘겨도 이어짐 (SCR-00 6장) | 11 |
| 원문 위치 | `<파일 이름> · <절 또는 표> · <행>`. PDF는 파일 이름 뒤에 `<n>쪽`(응답 `page`, add-pdf-page-location). 파일 이름은 `/documents`의 `file_no → file_name`. 위치가 여럿이면 첫 위치 + "외 n곳" | RFP01 Bidding Forms.docx · 표 4 · 7100행 외 1곳 / spec.pdf · 2쪽 · 1.1 GENERAL · 12행 |
| 요구값·제품값 | API 원문 글자(`*_raw`)를 그대로. 화면에서 숫자를 다시 쓰거나 단위를 바꾸지 않는다 (CR-10) | 4000 A |
| 금액 | 계산된 숫자(`total_usd`)만 `$` + 천 단위 쉼표 | $1,240,400 |
| 비율 | 소수 첫째 자리 반올림 + `%` | 21 % |
| 빈 값 | `—`. 확인이 필요한 빈 값은 "확인 필요" 배지 (CR-04) | — |

## 4. 근거와 꼬리표 (공통 규칙 CR 화면 쪽)

- 시스템이 낸 값의 줄에는 원문 위치를 보여 주고, 누르면 원문을 연다(`Evidence`). 위치 없는 줄은 API가 내지 않으므로 화면에서 만들지 않는다 (CR-02·03).
- 팀 가정 값이 들어간 줄에는 "팀 가정" 꼬리표 (CR-06, `Assumed`).
- 위험 조건·일탈·질의·보증값·제안 포인트는 사람이 확정하기 전까지 "후보" 꼬리표 (CR-08).
- 언어 모델이 쓴 문장 옆에는 숫자 대조 결과(`number_check`)를 보여 주고, 불일치면 경고 배지 (CR-07).

## 5. 권한과 사용자

- 로그인은 없다. 머리글에서 사용자를 고르고, 고른 사용자의 역할로 권한을 정한다.
- 역할별로 할 수 있는 동작: 후보 확정·수정·반려·채택·버림, 검토 정보 고치기, 결재 상신, 상신 취소는 엔지니어. 승인·반려는 지정된 결재자(승인자). 할 일 상태 바꾸기는 그 역할 담당자.
- 다른 역할로 볼 때는 같은 화면을 읽기 전용으로 보여 준다.
- 지금 백엔드는 승인·반려와 할 일 상태만 역할을 검사하고, 후보 확인 동작(`POST /actions`)은 사용자가 있는지만 본다. 엔지니어 전용 동작은 화면이 막는다.

## 6. 예시 화면 규칙 (2026-10-28 결정)

- 예시 화면은 목업 레이아웃 그대로, 데이터는 프런트 안의 고정 예시 데이터로 만든다. API를 부르지 않는다.
- 화면 맨 위에 "예시 화면 · 실제 데이터와 연결되지 않음" 띠를 항상 보여 준다. 화면 안 버튼은 눌러도 저장하지 않는다.
- 예시 데이터에는 고객사 RFP 원문 문장, 실제 고객사명·연락처·단가를 넣지 않는다(AGENTS.md 6장).
- 금액(입찰 이력의 금액·가격 평가)은 예시 화면에서도 "영업 권한 필요"처럼 가린 채로 둔다(가격 계산은 범위 밖).
- 실제 화면 안의 일부 예시 영역(예: 홈의 교육·행사 카드)도 같은 띠를 그 영역에 붙인다.
