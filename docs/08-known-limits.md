# 알려진 한계

> README에서 옮긴 표입니다. 면접이나 리뷰에서 먼저 짚을 만한 것을 숨기지 않고 적었습니다.

| 한계 | 지금 상태 | 실제로 쓴다면 |
|---|---|---|
| 인증이 단순함 | 아이디·비밀번호 로그인과 DB 세션(쿠키 `s2w_session`, HttpOnly·SameSite=Lax, 기본 8시간 고정 만료)이 있습니다(11-23, `add-session-auth`). 모든 API가 로그인을 요구하고(`/api/health`·`/api/auth/login`만 공개, 경로마다 401인지 시험), 요청 본문·주소의 사용자 번호는 받지 않아 결재·확정 이력의 "누가"는 로그인한 사람입니다. 다만 비밀번호 정책·잠금·재설정 메일, 사용자 관리 화면이 없고 비밀번호는 명령(`rfp-db set-password`)으로만 정합니다. 부서 담당자(견적·품질·영업)도 같은 방식이며 SSO는 없습니다 | 사내 SSO(OIDC)로 바꾸고 세션 발급만 남기기, 로그인 실패 잠금, 사용자·역할 관리 화면, HTTPS 배포 때 `RFP_COOKIE_SECURE=true` |
| 처리기 살아 있음은 진행과 따로 | 밀려난 실행이 결과를 쓰던 빈틈("확인한 뒤 쓰기")은 11-23 `update-run-fencing`으로 닫았습니다. 처리 흐름의 연결은 커밋할 때마다 같은 트랜잭션 안에서 검토 행을 잠그고(`FOR UPDATE`) 토큰을 다시 읽어, 자기 토큰이 아니면 그 저장을 되돌리고 멈춥니다(토큰 확인 뒤·저장 전에 다시 넣는 시험이 고치기 전 판정 18건 저장 → 고친 뒤 0건). 남은 한계: 처리기 살아 있음은 별도 스레드가 보내므로, AI 응답을 기다리며 멈춘 작업도 살아 있는 것으로 보입니다(AI 요청 시간 제한 120초로 막음) | 진행이 일정 시간 없으면 멈춤으로 보기 |
| 평가셋이 작고 쉬움 | 공개 평가셋 78문항은 처음에 Claude 초안 정답이었고, 11-16 최민정이 문항 68개를 하나씩 확인해 사람 확인으로 바꿨습니다(Claude 초안과 다른 정답 0개, 검수표 `data/eval/human_review/`). 다만 합성 문장이고 문항이 적어(유형 30, 도우미 8) 한 문항이 3 ~ 12 %p라, 숫자는 "같은 문제에서 전보다 나빠졌는가"를 보는 데 쓰고 절대 품질로 읽지 않습니다 | 실제 RFP에서 어려운 줄을 더해 문항 늘리기, 두 번째 사람의 확인 |
| 평가 비용 상한은 시작 전 어림만 | 프롬프트 평가 CI는 11-16 저장소에 키를 등록한 뒤부터 실제로 돕니다(그 전 PR 4건은 "평가하지 않음"으로 건너뜀). 비용 상한(`RFP_EVAL_MAX_KRW`)은 시작 전 어림 비용으로만 막아, 회귀 시연 PR #25는 출력 토큰이 3배로 늘며 상한 1,000원을 넘은 1,586원이 들었습니다 | 실행 중 누적 비용이 상한을 넘으면 멈추기 |
| 다른 회사 모델은 재지 않음 | 모델 비교 도구(FR-23)는 만들었지만, 실측은 Gemini 3.8 Flash와 로컬 3B 모델뿐입니다 | Claude·GPT 키로 같은 평가셋 비교 |
| "확인 필요"가 많음 | 실제 입찰 서식 1건에서 비교한 줄의 60 %(2,718 / 4,515)가 확인 필요이고, 그중 87 %는 항목 사전에 없는 항목입니다. 추측하지 않는 대가입니다([05](05-evaluation.md)) | 항목 사전 표현 넓히기(임베딩이 이미 후보를 냄) |
| 배포 없음, 화면 테스트는 CI 밖 | 로컬 Docker Compose로만 돌립니다. 프런트 단위 테스트는 없고, 화면 E2E(Playwright)는 PR 전에 로컬에서 돌립니다 | — |
| 코드 품질 수치 | SonarQube 이슈 115건을 전수 분류했고, 실제 버그는 0건이었습니다. 23건은 고쳤고, 92건은 오탐 15·의도했거나 위험 낮음 58·고치면 동작이 바뀌는 것 19로 나눠 근거를 남겼습니다. 대시보드의 미해결 이슈가 0이 된 것은 고친 23건과 근거를 남긴 92건을 합친 결과입니다([품질 보고서](quality/sonarqube-report.md)) | 동작이 바뀌는 19건은 보고서 6장 "추후 개선" |
