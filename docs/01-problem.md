# 01. 문제 정의

## 누구의 어떤 일인가

전력 설비(GIS 개폐장치, 차단기, 변압기, 배전반 등) 입찰에서 발주처는 수백 쪽짜리 **RFP**(제안 요청서)를 보냅니다. 한 묶음 안에 기술 사양서, 입찰 서식, 장비별 데이터시트, 계약 조건이 섞여 있습니다.

이 문서를 받는 사람은 제조사의 **입찰 기술 검토 엔지니어**입니다. 엔지니어는 세 가지를 해야 합니다.

1. 우리 제품에 걸리는 **요구사항을 빠짐없이** 찾는다.
2. 우리 제품이 그 요구를 **맞추는지 판정**한다.
3. 못 맞추는 것은 **일탈 목록**(deviation list)으로, 문서가 애매하거나 값이 서로 다른 것은 **고객 질의 목록**(clarification list)으로 정리해 입찰서와 함께 낸다.

여기에 견적·품질·영업 부서가 처리할 줄(지체상금, 시험 입회, 제조사 자격 서류 등)을 골라 넘기는 일, 데이터시트 빈칸에 우리 제품의 보증값을 채우는 일이 더해집니다.

## 데이터로 확인한 어려움

운영진이 교육용으로 가림 처리해 준 **실제 RFP 22개**(docx, 약 52만 단어, 표 1,360개)를 팀이 전수 분석해, 이 일이 왜 어려운지를 숫자로 확인했습니다.

| No | 어려움 | 데이터에서 확인한 것 |
|---|---|---|
| P1 | 읽을 양이 너무 많다 | 요구사항 후보 줄이 약 11,540줄(문장 약 7,140 + 데이터시트 칸 약 4,270 + 공급사 답안 134). 가장 긴 문서는 약 21만 단어 |
| P2 | 놓치면 계약 조건이 되는 조항이 숨어 있다 | "일탈 목록에 적지 않은 차이는 받아들인 것으로 본다" 같은 포괄 조항. "deemed(~로 본다)"만 약 25줄 |
| P3 | 같은 항목인데 값이 다르다 | 한 문서 안에서 가스 누설률이 두 값으로 적힘, 같은 사업의 두 문서에서 UPS 용량이 다름. 두 값이 100줄 넘게, 어떤 경우는 7,000줄 떨어져 있음 |
| P4 | 숫자끼리 계산이 안 맞는다 | 230 kV 차단기: 차단 전류 50 kA인데 최대 순간 전류 100 kA (공학 규칙으로는 125 kA여야 함). 두 문서에 똑같이 반복 |
| P5 | 데이터시트의 40 %는 비교가 아니라 "채우는" 일이다 | 데이터시트 칸 약 4,350개 중 빈칸 약 1,680개(39 %), "규격대로"처럼 규격에 맡긴 칸 약 190개 |
| P6 | 문서 구조를 컴퓨터가 바로 알 수 없다 | 제목 스타일이 없고 장·절은 번호로만 구분. 한 표가 쪽마다 끊겨 Word 표 4개로 나뉨 |

## 지금 방식의 한계

| 지금 방식 | 한계 |
|---|---|
| Word·PDF를 직접 읽고 엑셀에 옮겨 적기 | 멀리 떨어진 값끼리 비교하기 어렵고, 단위를 빼고 숫자만 옮기는 실수가 잦음 |
| Ctrl+F로 단어 검색 | 미리 의심하는 단어만 찾음. 같은 뜻의 다른 표현(누설·누기·leakage)을 놓치고, 계산 관계는 알 수 없음 |
| 일반 AI 챗봇에 문서를 넣고 질문 | 우리 제품 정보를 모름. 근거 위치가 불안정함. 빈칸에 그럴듯한 값을 지어낼 위험 |

LS 영업 현업 멘토링에서는 "기술 검토는 보통 7~10일 걸린다"는 이야기를 들었습니다. 다만 같은 조건에서 사람과 시스템을 비교해 재지는 않았으므로 **처리 시간 단축률은 주장하지 않습니다.**

## 해결할 문제 (시스템 정체성)

처음 주제는 "RFP 견적 자동산출"이었습니다. 실제 RFP를 분석해 보니 가격표 자체보다 **기술 조건을 빠짐없이 검토하는 일**이 훨씬 크고 위험했습니다. 10-19 팀 회의에서 시스템의 중심을 "견적 계산"에서 **"기술 검토 지원"**으로 옮겼고, 10-22 현업 면담("요약만으로는 일반 생성형 AI와 차이가 없다", "가격 경쟁보다 기술적 가치")을 반영해 **"내세우기"**를 더했습니다.

> 기술 검토 엔지니어가 수백 쪽 RFP에서 우리 제품에 걸리는 요구사항과 위험·불일치 조건을 **빠짐없이 찾고(지키기)**, 우리 제품이 요구보다 나은 점을 **근거와 함께 찾아(내세우기)**, 일탈 목록·고객 질의 목록과 기술 제안 포인트를 만들도록 돕는다.

- **지키기**: 요구사항 표, 위험 조건 후보, 적합성 판정, 일탈·질의 목록 초안, 보증값 후보
- **내세우기**: 판정에서 찾은 여유(예: 단시간 전류 요구 1초 ↔ 우리 제품 3초), 변압기 손실 환산 우위, 우리 제품군의 현장 대응 이력을 모은 **기술 제안 포인트**
- **견적 연결**은 손실 환산 계산까지만 합니다. 가상 단가로 가격을 만드는 일은 근거가 없어 범위에서 뺐습니다.

## 사용자

| 구분 | 사용자 | 시스템에서 받는 것 |
|---|---|---|
| 주 사용자 | 입찰 기술 검토 엔지니어 | 요구사항 표, 위험 조건 목록, 적합성 표, 보증값 후보, 일탈·질의 목록 초안, 제안 포인트 후보 |
| 전달받는 사람 | 견적 / 품질 / 영업 담당 | 비용 영향 줄과 손실 환산 / 시험 줄 / 제조사 자격 줄과 채택된 제안 포인트 (시스템이 부서 메일로 보냄, 따로 로그인하지 않음) |
| 승인자 | 입찰 책임자 | 승인 기준에 걸린 사유와 결재 화면 |

## 지키기로 한 원칙

| 목표 | 내용 |
|---|---|
| G1 | 요구사항과 위험 조건을 빠짐없이 찾는다 |
| G2 | 판정과 일탈·질의 목록을 **근거(원문 위치)와 함께** 만든다 |
| G3 | 숫자와 판정은 **같은 입력에 늘 같은 결과**가 나온다 |
| G4 | 사람이 확인·승인하기 전에는 아무것도 확정되지 않는다 |
| G5 | **없는 값을 지어내지 않는다** (빈칸은 비우고 "확인 필요") |
| G6 | 근거 없는 강점은 만들지 않는다 |

이 원칙이 아키텍처의 거의 모든 결정을 정했습니다([02 아키텍처](02-architecture.md), [03 ADR](03-adr.md)).

## 범위 밖

가격 계산·할인, 도면 기호 해석, 단위 환산, 경쟁 제품 비교는 만들지 않았습니다. 국제 규격(IEC 등) 원문은 유료라 없으므로, "As per IEC"처럼 규격에 맡긴 요구는 값을 찾지 않고 "확인 필요"로 모읍니다.
