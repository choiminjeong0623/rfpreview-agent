# review-run Specification

## Purpose
RFP 검토 한 번을 하나의 실행으로 묶어, 결과가 어떤 입력·사전·제품표에서 나왔는지 추적하고 같은 입력이면 같은 결과를 내게 한다.

## Requirements

### Requirement: 실행 생성
시스템은 검토를 시작할 때 실행 하나를 만들고 대상 문서, 시작한 사람, 사전·제품표 판을 기록해야 한다(SHALL). 이 실행에서 나온 모든 결과는 실행에 묶여야 한다(SHALL).

#### Scenario: 파일 1로 검토 시작
- **WHEN** 엔지니어가 파일 1로 검토를 시작하면
- **THEN** 실행 하나가 PROCESSING 단계로 생기고 사전 판이 기록된다

### Requirement: 재현성
시스템은 같은 문서·같은 사전 판·같은 제품표로 다시 실행하면 숫자와 판정 결과가 같아야 한다(SHALL, CR-11, NFR-02).

#### Scenario: 같은 문서 두 번
- **WHEN** 같은 문서를 같은 사전 판으로 두 번 처리하면
- **THEN** 두 실행의 요구사항 수, 값, 위험 조건 후보가 같다

### Requirement: AI 오류 처리
시스템은 AI 연결 오류, 시간 초과, 서버 오류에 정해진 횟수만 재시도하고, 그래도 실패하면 실행을 멈추고 "처리 실패 — 다시 시도"를 알려야 한다(SHALL, CR-12). 답의 형식이 틀리면 같은 질문을 다시 묻지 않는다. 키·권한·모델 설정 오류는 다시 묻지 않고 바로 멈추고 "AI 키 또는 모델 설정 오류 — 설정 확인"을 알려야 한다(SHALL). [제안 11-01: 오류 종류별 처리]

#### Scenario: AI 키 없음
- **WHEN** 언어 모델 키 없이 검토를 실행하면
- **THEN** AI 보조 단계는 건너뛰고 코드 규칙 결과로 엔지니어 검토(ENGINEER_REVIEW) 단계까지 간다

#### Scenario: 계속 실패
- **WHEN** AI 호출이 재시도 횟수를 넘겨 실패하면
- **THEN** 실행은 FAILED가 되고 실패한 단계와 "처리 실패 — 다시 시도"가 보인다

#### Scenario: 형식이 틀린 답은 다시 묻지 않음
- **WHEN** 언어 모델이 검사에 맞지 않는 답을 내면
- **THEN** 같은 질문은 한 번만 보내고 재시도 수는 0이다

#### Scenario: 키 오류는 바로 멈춤
- **WHEN** 언어 모델이 키 오류(401)를 돌려주면
- **THEN** 요청 1번 뒤 실행은 FAILED가 되고 "AI 키 또는 모델 설정 오류 — 설정 확인"이 보인다

### Requirement: 긴 문서는 절 단위로 처리
시스템은 문서를 통째로 AI에 넣지 않고 절 단위로 처리하며, 처리한 절의 결과를 저장해 재사용해야 한다(SHALL, NFR-05). 저장된 결과는 처리 판과 파일 내용이 모두 같을 때만 다시 써야 하며, 파일 이름이나 파일 번호가 같아도 내용이 다르면 새로 처리해야 한다(SHALL, CR-11). 같은 파일을 여러 검토가 거의 동시에 처리해 저장이 겹치면 늦은 쪽은 먼저 저장된 결과를 다시 쓰고 멈추지 않아야 한다(SHALL).

#### Scenario: 가장 긴 문서
- **WHEN** 파일 2를 처리하면
- **THEN** 처리가 끝나고 AI 호출 입력은 모두 절 단위이다

#### Scenario: 이름이 같고 내용이 다른 파일
- **WHEN** 파일 목록의 같은 이름으로 내용이 다른 두 파일을 차례로 검토하고, 두 번째 파일로 한 번 더 검토하면
- **THEN** 두 파일은 같은 파일 번호이지만 두 번째 파일은 새로 처리되고, 세 번째 검토는 두 번째 처리 결과를 다시 쓴다

#### Scenario: 같은 파일을 거의 동시에 두 번 올림
- **WHEN** 두 검토가 같은 파일을 같은 처리 판으로 처리하다 저장이 겹치면
- **THEN** 늦은 검토는 새 문서를 만들지 않고 먼저 저장된 문서로 판정까지 끝난다

### Requirement: 검토 정보
시스템은 실행마다 사람이 입력한 검토 정보(사업명, 검토명, 고객사, 국가, 제출 마감일, 담당 엔지니어)를 저장하고 검토를 시작할 때와 시작한 뒤에 받을 수 있어야 한다(SHALL). 제출 마감일은 시작할 때 꼭 받아야 하며, 없으면 실행을 만들지 않고 "제출 마감일을 입력해 주세요." 오류를 내야 한다(SHALL). 나머지 칸은 비어 있어도 되며, 시스템이나 언어 모델이 빈칸을 채우지 않아야 한다(MUST NOT, CR-04). 담당 엔지니어가 비어 있고 시작한 사람이 엔지니어 역할이면 그 사람으로 둔다. 담당 엔지니어는 엔지니어 역할 사용자만 될 수 있다(SHALL).

#### Scenario: 검토 정보와 함께 시작
- **WHEN** 엔지니어가 사업명 "Thai Binh", 검토명 "115·230 kV GIS 변전소 신설", 고객사, 국가, 마감일 2026-10-30을 넣고 파일 1로 검토를 시작하면
- **THEN** 실행 요약에 다섯 값이 그대로 보이고 담당 엔지니어는 시작한 엔지니어다

#### Scenario: 검토 정보 없이 시작
- **WHEN** 마감일만 넣고 다른 검토 정보는 넣지 않고 검토를 시작하면
- **THEN** 실행은 그대로 시작되고 마감일 말고 검토 정보 칸은 모두 비어 있다

#### Scenario: 마감일 없이 시작
- **WHEN** 마감일을 넣지 않고 검토를 시작하면
- **THEN** "제출 마감일을 입력해 주세요." 오류가 나고 실행은 만들어지지 않는다

#### Scenario: 엔지니어가 아닌 담당자
- **WHEN** 견적 담당 사용자를 담당 엔지니어로 넣으면
- **THEN** 담당 엔지니어는 엔지니어만 될 수 있다는 오류가 나고 바뀌지 않는다

### Requirement: 검토 정보 고치기와 이력
시스템은 실행 단계와 관계없이 검토 정보를 고치게 하고, 고칠 때마다 이전 값·새 값·작업자·시각을 수정 이력에 남겨야 한다(SHALL). 제출 마감일은 비우도록 고칠 수 없어야 한다(SHALL). 검토 정보는 판정·후보 계산에 쓰지 않아야 한다(MUST NOT).

#### Scenario: 마감일을 바꿈
- **WHEN** 엔지니어가 마감일을 2026-10-30에서 2026-11-02로 고치면
- **THEN** 실행 요약의 마감일이 바뀌고 이력 1건(이전 값, 새 값)이 남는다

#### Scenario: 마감일 비우기
- **WHEN** 엔지니어가 마감일을 빈 값으로 고치면
- **THEN** 마감일은 비울 수 없다는 오류가 나고 마감일과 이력은 그대로다

#### Scenario: 판정은 그대로
- **WHEN** 검토명과 고객사를 고친 뒤 판정 목록을 다시 보면
- **THEN** 판정 줄 수와 결과가 고치기 전과 같다

### Requirement: 실행 목록 응답
시스템은 실행 목록과 실행 요약에 검토 번호(`RV-<시작 연도>-<실행 번호 세 자리>`), 검토 정보, 담당 엔지니어 이름을 넣고, 실행 목록에는 요구사항·위험 조건·일탈 후보·제안 포인트 개수를 함께 넣어야 한다(SHALL).

#### Scenario: 목록의 개수
- **WHEN** 처리가 끝난 실행이 있는 상태에서 실행 목록을 부르면
- **THEN** 그 줄의 요구사항·위험 조건·일탈 후보·제안 포인트 개수가 실행 요약의 개수와 같다

#### Scenario: 검토 번호
- **WHEN** 2026년에 시작한 실행 25번을 부르면
- **THEN** 검토 번호는 "RV-2026-025"다

### Requirement: 목록 API의 전체 개수
시스템은 나눠서 주는 목록(요구사항, 판정, 보증값 후보)에 거름 조건을 적용한 전체 개수를 함께 알려야 한다(SHALL).

#### Scenario: 판정 목록 나눠 받기
- **WHEN** 일탈 후보만 거르고 10줄씩 판정 목록을 부르면
- **THEN** 10줄 이하가 오고 일탈 후보 전체 개수가 함께 온다

### Requirement: 판정 목록 거르기와 판정 순서
시스템은 판정 목록을 주 유형, 검색어(항목 이름·영문 항목명·원문 문장), 확정 안 한 것만으로 거르고, 요청하면 판정 순서(일탈 후보 → 질의 후보 → 확인 필요 → 작성 필요 → 준수, 같은 판정 안에서는 판정 번호 순)로 정렬해야 한다(SHALL). 걸러진 전체 개수는 지금처럼 함께 알려 준다. 판정 줄에는 주 유형 코드와 이름을 넣는다(SHALL).

#### Scenario: 확정 안 한 일탈 후보만
- **WHEN** 일탈 후보 4건 중 1건을 확정한 실행에서 일탈 후보이면서 확정 안 한 판정만 요청하면
- **THEN** 3건이 오고 전체 개수도 3이다

#### Scenario: 판정 순서로 받기
- **WHEN** 판정 순서로 목록을 요청하면
- **THEN** 일탈 후보가 모두 질의 후보보다 앞에 오고, 준수는 맨 뒤에 온다

#### Scenario: 검색어로 거르기
- **WHEN** 검색어 "busbar"로 요청하면
- **THEN** 영문 항목명에 busbar가 들어간 판정만 온다

### Requirement: 판정 칩 건수
시스템은 실행의 현재 판정을 판정 값마다 센 건수, 확정 안 한 판정 수, 그중 준수 수를 한 번에 알려 줘야 한다(SHALL). 반려한 판정은 세지 않는다.

#### Scenario: 칩 건수
- **WHEN** 판정 칩 건수를 요청하면
- **THEN** 판정 값마다의 건수 합이 전체 판정 수와 같고, 확정 안 한 수는 확정·수정한 판정을 뺀 수다

### Requirement: 위험 조건 항목 이름
시스템은 위험 조건 목록의 값 불일치 줄에 표준 항목의 한국어 이름을 함께 넣어야 한다(SHALL). 항목이 없는 위험 조건(포괄 조항, 범위 모호)은 이름을 비워 둔다.

#### Scenario: 값 불일치 항목 이름
- **WHEN** 가스 누설률 값이 문서마다 다른 실행의 위험 조건 목록을 요청하면
- **THEN** 값 불일치 줄의 항목 이름은 "가스 누설률"이고, 포괄 조항 줄의 항목 이름은 비어 있다

### Requirement: 손실 환산 종류별 가산액
시스템은 손실 환산 목록에 무부하·부하·보조마다 단가 × 손실값으로 계산한 가산액과 단가 행의 원문 위치를 함께 넣어야 한다(SHALL). 손실값이 없는 종류의 가산액과, 단가 단위가 $/kW가 아닌 경우의 가산액은 비워 둔다(CR-10).

#### Scenario: 종류별 가산액과 단가 위치
- **WHEN** 단가 4,500·3,200·1,300 $/kW 행이 있고 손실값을 60·300·8 kW로 넣은 실행의 손실 환산 목록을 요청하면
- **THEN** 종류별 가산액은 270,000·960,000·10,400이고 그 합이 가산액 합계와 같으며, 단가 행 위치 3개가 함께 온다

### Requirement: 이력 대상 이름
시스템은 실행의 수정 이력 줄마다 바뀐 대상의 이름을 함께 넣어야 한다(SHALL). 판정·보증값은 항목 이름(없으면 영문 항목명), 위험 조건은 표현(없으면 항목 이름), 제안 포인트는 근거, 일탈·질의 목록은 문장 앞부분, 손실 환산은 비교 제품이다. 검토 실행과 비교 제품 바꾸기 줄은 비워 둔다.

#### Scenario: 이력 대상 이름
- **WHEN** 질의 후보 판정을 준수로 바꾸고, 다른 실행에서 포괄 조항 위험 조건을 문제 없음으로 닫은 뒤 이력을 요청하면
- **THEN** 판정 줄의 대상 이름은 그 판정의 항목 이름이고, 위험 조건 줄의 대상 이름은 그 표현이다

### Requirement: 문서 읽기 점검 목록
시스템은 실행마다 시스템이 제대로 읽지 못한 곳을 점검 줄로 돌려줘야 한다(SHALL). 종류는 표(칸 역할을 못 찾은 표), 그림(문서 안 그림, 읽지 않은 스캔 문서), 단위(단위 없는 값을 표나 절마다 묶음), 위치(번호가 끊긴 절, 같은 문서에서 번호가 두 번 나온 절)이고, 줄마다 종류, 무엇, 파일, 위치, 문제, 할 일, 확인한 사람과 시각을 넣는다. 같은 입력이면 같은 줄이 같은 순서로 나온다(CR-11).

#### Scenario: 읽지 못한 곳 목록
- **WHEN** 칸 역할을 못 찾은 표, 그림 1개, 단위 없는 값, 같은 번호가 두 번 나온 절이 있는 문서로 실행하고 점검 목록을 요청하면
- **THEN** 표·그림·단위·위치 줄이 이 순서로 오고, 각 줄에 파일 이름과 줄 번호가 든 위치와 할 일이 있으며 확인한 사람은 비어 있다

### Requirement: 문서 읽기 점검 확인
시스템은 엔지니어가 담당자 확인 단계에서 점검 줄을 "직접 확인함"으로 표시하거나 되돌릴 수 있게 하고, 두 동작을 모두 수정 이력에 남겨야 한다(SHALL). 승인 화면 정보에는 확인하지 않은 점검 줄 수를 넣는다.

#### Scenario: 점검 확인과 되돌리기
- **WHEN** 엔지니어가 점검 줄 하나를 확인했다가 되돌리면
- **THEN** 확인했을 때는 그 줄에 확인한 사람과 시각이 있고 확인 안 한 수가 1 줄며, 되돌리면 다시 비고, 이력에 두 줄이 그 점검 줄 이름으로 남는다

#### Scenario: 담당자 확인 단계에서만 확인
- **WHEN** 결재 상신한 실행의 점검 줄을 확인하려 하면
- **THEN** 409 오류로 거절한다

### Requirement: 처리 세부 진행 기록
시스템은 처리 중인 실행의 문서 읽기 단계에서 지금 하는 세부 일(문서 종류 확인, 절·표 나누기, 요구사항 뽑기, AI 문장 구분, 저장, AI 유형 붙이기), 몇 번째 파일인지, AI 일은 끝난 줄 수와 전체 줄 수를 처리 도중에 바로 기록해야 한다(SHALL). 단계나 세부 진행이 바뀔 때마다 마지막 진행 시각을 기록하고, 단계가 바뀌면 세부 진행을 지운다. 진행 기록이 실패해도 처리는 계속한다. 실행 요약과 실행 목록은 세부 진행과 마지막 진행 시각을 함께 준다. 판정·추출 결과는 바뀌지 않는다(CR-11). [제안]

#### Scenario: 유형 붙이기 진행 개수
- **WHEN** 규칙으로 유형을 정하지 못한 요구사항이 있는 문서를 AI와 함께 처리하면
- **THEN** 처리 도중 "AI 유형 붙이기" 세부 진행이 기록되고, 끝난 줄 수는 0보다 크고 전체 줄 수 이하이며 마지막 기록에서 전체 줄 수와 같고, 파일 순번은 1 / 1이다

#### Scenario: 단계가 바뀌면 세부 진행을 지움
- **WHEN** 처리가 끝난 실행의 실행 요약을 부르면
- **THEN** 세부 진행은 비어 있고 마지막 진행 시각이 있다

#### Scenario: 목록에도 세부 진행
- **WHEN** 문서 읽기 단계에서 유형 붙이기 120 / 400줄까지 기록된 실행이 있을 때 실행 목록을 부르면
- **THEN** 그 줄의 세부 진행은 AI 유형 붙이기, 120, 400이다

### Requirement: 검토 취소
시스템은 처리 중인 검토에 사람의 취소 요청을 받아 요청 시각과 요청자를 남기고, 처리 흐름이 다음 진행을 기록할 때 멈추게 해야 한다(SHALL). 멈춘 검토는 처리 실패가 되고 멈춘 단계와 "○○이(가) 분석을 취소했습니다" 문장을 남긴다. 멈춘 문서의 반쯤 만든 결과는 저장하지 않는다. 마지막 진행이 10분 넘게 없으면 요청 즉시 처리 실패로 바꾼다. 처리 중이 아닌 검토의 취소 요청은 거절한다. [제안]

#### Scenario: 처리 중 취소
- **WHEN** 문서 읽기 단계를 처리하는 중인 검토에 취소를 요청하면
- **THEN** 처리가 다음 진행 기록에서 멈추고 검토는 처리 실패, 멈춘 단계 문서 읽기, 취소 문장과 취소 표시가 남으며 그 문서는 저장되지 않는다

#### Scenario: 멈춘 검토 취소
- **WHEN** 마지막 진행이 11분 전인 처리 중 검토에 취소를 요청하면
- **THEN** 바로 처리 실패가 되고 "진행이 멈춰" 문장이 남는다

#### Scenario: 끝난 검토는 취소 못 함
- **WHEN** 담당자 확인 단계인 검토에 취소를 요청하면
- **THEN** 409 오류로 거절하고 검토는 그대로다

### Requirement: 검토 다시 시도
시스템은 처리 실패한 검토(취소 포함)에 사람의 다시 시도 요청을 받아, 처음 시작할 때와 같은 파일과 같은 사람 분류로 같은 검토를 다시 처리해야 한다(SHALL). 저장된 흐름이 있으면 끝난 단계는 건너뛰고 멈춘 단계부터 이어서 처리하고, 없으면 처음부터 처리하되 이미 처리한 문서는 다시 쓴다(NFR-05). 다시 시도하면 처리 중으로 바뀌고 멈춘 단계·오류 문장·취소 표시를 지우며 다시 시도 횟수를 하나 늘린다. 처리 실패가 아니거나 다시 돌릴 파일 정보가 없으면 거절한다. [제안] [이어서 처리: 제안 11-01, C2]

#### Scenario: 취소한 검토 다시 시도
- **WHEN** 문서 읽기에서 취소한 검토를 다시 시도하면
- **THEN** 같은 검토 번호로 담당자 확인 단계까지 가고 판정이 나오며 다시 시도 횟수는 1이다

#### Scenario: 처리한 문서는 다시 씀
- **WHEN** 문서 두 개 가운데 첫 문서를 처리한 뒤 실패한 검토를 다시 시도하면
- **THEN** 첫 문서는 같은 문서로 다시 쓰이고 새 문서 줄은 두 번째 문서 하나만 생긴다

#### Scenario: 다시 돌릴 파일 정보 없음
- **WHEN** 파일 정보가 저장되지 않은 처리 실패 검토를 다시 시도하면
- **THEN** 409 오류와 다시 등록하라는 안내가 돌아오고 검토는 그대로다

#### Scenario: 멈춘 단계부터 이어서
- **WHEN** 위험 조건 단계까지 끝내고 판정 단계에서 실패한 검토를 다시 시도하면
- **THEN** 문서·짝·위험 조건 단계는 다시 돌지 않고(위험 설명 AI 호출 없음) 판정 단계부터 이어서 담당자 확인까지 가며, 실행 기록에 이어서 시작한 단계가 판정으로 남는다

#### Scenario: 이어서 해도 결과가 같음
- **WHEN** 같은 파일을 처음부터 끝까지 돌린 검토와 중간에 실패한 뒤 이어서 다시 시도한 검토를 비교하면
- **THEN** 판정·위험 조건·일탈 후보 수가 같다

### Requirement: 실행 기록 저장
시스템은 검토 처리마다 언어 모델 요청 수(재시도 포함), 재시도 수, 입력·출력·생각 토큰, 이전 처리 결과를 다시 쓴 문서 수, 단계마다 시작·끝 시각을 저장해야 한다(SHALL). 처리가 실패해도 그때까지의 값을 저장하고, 다시 시도하면 사용량은 더하고 단계 시각은 시도마다 따로 남긴다. 판정·추출 결과는 바뀌지 않는다(CR-11). [제안]

#### Scenario: 실행 기록 저장
- **WHEN** 언어 모델과 함께 문서 하나로 검토를 끝까지 처리하면
- **THEN** 요청 수는 실제 요청 수, 재시도 0, 토큰은 요청마다 받은 토큰의 합이고, 문서 읽기부터 할 일 전달까지 단계마다 걸린 시간이 남는다

#### Scenario: 같은 파일을 다시 처리
- **WHEN** 같은 파일로 검토를 두 번 처리하면
- **THEN** 두 번째 실행의 다시 쓴 문서 수는 1이고 요청 수는 첫 번째보다 적다

#### Scenario: AI 재시도 기록
- **WHEN** 언어 모델이 계속 실패해 처리가 멈추면
- **THEN** 요청 3, 재시도 2와 실패 단계가 남고, 멈춘 단계의 끝 시각도 남는다

### Requirement: 실행 기록 응답
시스템은 실행 기록 API로 검토마다 검토 번호와 이름, 상태, 시작·끝 시각, 걸린 시간, 모델, 사전 판, 요청·재시도 수, 토큰, 추정 비용, 문서 수와 다시 쓴 문서 수, 요구사항·판정 수, 다시 시도 횟수, 단계별 걸린 시간을 최근 실행부터 줘야 한다(SHALL). 추정 비용은 모델 단가(팀 가정, 1$ = 1,500원)로 계산하고 팀 가정 표시를 붙인다(CR-06). 단가표에 없는 모델은 비용을 비우고, 언어 모델 없이 돈 실행은 0원이다. [제안] [확인 필요: 모델 단가]

#### Scenario: 단가로 어림한 비용
- **WHEN** gemini-3.8-flash로 입력 73,556 · 출력 28,775 · 생각 77,778 토큰을 쓴 실행의 비용을 계산하면
- **THEN** 약 680원(650~720원)이다

#### Scenario: 언어 모델 없이 돈 실행
- **WHEN** 언어 모델 키 없이 처리한 실행을 실행 기록에서 보면
- **THEN** 요청 0, 비용 0원이고 팀 가정 표시가 없다

### Requirement: 검토에 문서 추가
시스템은 담당자 확인 단계(결재 상신 전) 검토에 엔지니어가 docx 문서를 더하면, 처음 올린 파일과 분류에 더한 파일과 그 분류를 합쳐 같은 검토 번호로 다시 분석해야 한다(SHALL). 이미 처리한 문서는 다시 쓰고(NFR-05) AI를 다시 부르지 않는다. 이력에 "문서 추가"와 더한 파일 이름을 남긴다. 담당자 확인 단계가 아니면 409, 엔지니어가 아니면 403, 이미 있는 파일 이름이면 409로 거절하고 검토는 그대로 둔다. [제안]

#### Scenario: 문서를 더해 다시 분석
- **WHEN** 판정 1줄을 확정한 검토에 추가 문서 하나를 더하면
- **THEN** 같은 검토 번호로 담당자 확인 단계까지 다시 가고, 문서가 하나 늘며, 이력에 "문서 추가" 1건과 파일 이름이 남는다

#### Scenario: 상신한 검토에는 못 더함
- **WHEN** 결재 중인 검토에 문서를 더하려 하면
- **THEN** 409 오류와 "결재 상신 전" 안내가 돌아오고 검토는 결재 중 그대로다

#### Scenario: 같은 파일 다시 더하기
- **WHEN** 이미 이 검토에 있는 파일 이름으로 문서를 더하려 하면
- **THEN** 409 오류와 그 파일 이름이 돌아오고 검토는 담당자 확인 단계 그대로다

#### Scenario: 엔지니어만 더함
- **WHEN** 승인자가 문서를 더하려 하면
- **THEN** 403 오류가 돌아온다

### Requirement: 다시 분석할 때 위험 조건 바꾸기
시스템은 같은 검토를 다시 분석할 때(문서 추가·다시 시도) 위험 조건을 새로 만든 뒤 이전 것과 바꿔야 한다(SHALL). 종류·표현·항목·요구사항 묶음이 같은 위험 조건은 AI 설명과 근거 문장을 다시 쓰고 AI를 다시 부르지 않으며, 그 위험 조건에서 나온 목록 항목의 연결을 새 위험 조건으로 옮긴다. 다 끝난 검토를 다시 돌려도 목록 연결 때문에 실패하지 않는다. [제안]

#### Scenario: 같은 위험 조건은 AI 다시 안 부름
- **WHEN** AI 설명이 있는 위험 조건이 나온 검토에 문서를 더해 다시 분석하면
- **THEN** AI 설명 요청은 새로 생긴 위험 조건 수만큼만 가고, 근거 문장은 모두 지금 위험 조건에 붙어 있다

### Requirement: 지난 검토 비교 대상
시스템은 검토 하나에 대해 고객사 글자가 같은(앞뒤 공백·여러 칸 공백·대소문자 무시) 처리를 마친 다른 검토를 최근 것부터 비교 대상으로 돌려줘야 한다(SHALL). 대상마다 검토 번호, 사업명·검토명, 시작 시각, 단계, 판정 줄 수, 비교 제품을 준다. 이번 검토의 고객사가 비어 있으면 대상이 없다. [제안]

#### Scenario: 같은 고객의 지난 검토
- **WHEN** 고객사 "예시 송전회사"인 검토와 " 예시  송전회사 "인 검토, "다른 고객사"인 검토가 있고 두 번째 검토의 비교 대상을 요청하면
- **THEN** 첫 번째 검토만 대상으로 오고 검토 번호, 판정 줄 수, 비교 제품이 함께 온다

#### Scenario: 고객사가 비어 있음
- **WHEN** 고객사를 넣지 않은 검토의 비교 대상을 요청하면
- **THEN** 대상이 없고 고객사도 비어 온다

### Requirement: 지난 검토 비교
시스템은 두 검토의 지금 판정 줄을 같은 설비(제품군·설비 최고 전압)·같은 항목(표준 항목·표의 항목 이름)으로 짝지어, 값이나 판정이 다른 줄을 값 바뀜, 이번에만 있는 줄을 새로 생김, 지난번에만 있는 줄을 사라짐으로 돌려줘야 한다(SHALL). 줄마다 설비, 항목, 지난·이번 값, 지난·이번 판정, 코드가 쓴 참고 문장을 주고, 값과 판정이 같은 줄은 숨긴 수로 준다. 사람이 수정한 판정은 수정 값으로, 반려한 판정은 뺀다. 올라감·내려감은 단위 글자가 같을 때만 쓴다(CR-10). 같은 두 검토면 같은 결과다(CR-11). 같은 검토끼리는 400, 없는 검토는 404. [제안]

#### Scenario: 달라진 요구만
- **WHEN** 230 kV 주모선 4,000 A가 3,150 A로 바뀌고, 피더 3,500 A가 빠지고, 최대 순간 전류 125 kA가 새로 생긴 다음 입찰 검토를 지난 검토와 비교하면
- **THEN** 값 바뀜 1줄(245 kV GIS, 4000 A → 3150 A, "요구 값이 내려감"), 새로 생김 1줄(125 kA, "지난번에 없던 요구"), 사라짐 1줄(3500 A, "이번에는 요구 없음")만 오고 나머지는 숨긴 수로 온다

#### Scenario: 값은 같고 판정만 바뀜
- **WHEN** 지난 검토에서 정격 주파수 판정을 질의 후보로 수정한 뒤 비교하면
- **THEN** 그 줄은 값 바뀜 구분에 지난·이번 값이 같고, 참고 문장은 "요구 값 같음 · 판정 바뀜"이다

#### Scenario: 반려한 판정은 뺌
- **WHEN** 이번 검토에서 245 kV 정격 전압 판정을 반려한 뒤 비교하면
- **THEN** 이번 쪽에서 그 줄이 빠져 지난 쪽의 245 kV 줄이 사라짐으로 보인다

### Requirement: AI 묶음 동시 호출
시스템은 AI에 묻는 묶음(문장 구분·유형 붙이기·문장 초안의 40줄 묶음, 위험 조건 설명)을 정해진 개수(기본 4개, 설정으로 바꿈)만큼 동시에 보내야 한다(SHALL, NFR-10). 묶음마다 묻는 글은 차례로 보낼 때와 같고 답은 보낸 순서대로 받아 써서, 결과는 동시 개수와 상관없이 같아야 한다(SHALL, CR-11). 세부 진행의 끝난 줄 수는 묶음이 끝날 때마다 늘고, 실행 기록의 요청 수·토큰은 빠짐없이 센다. [제안]

#### Scenario: 동시 개수와 상관없이 같은 결과
- **WHEN** 같은 문서를 동시 1개와 동시 4개로 각각 AI와 함께 처리하면
- **THEN** 두 실행의 요구사항 구분·유형·위험 조건 설명·문장 초안이 같고, AI 요청 수와 토큰 합도 같다

#### Scenario: 동시에 보냄
- **WHEN** 묶음이 여러 개인 문서를 동시 4개로 처리하면
- **THEN** 같은 때에 진행 중인 AI 요청이 둘 이상 있고 넷을 넘지 않는다

#### Scenario: 묶음마다 진행
- **WHEN** 문장 구분 묶음이 셋 이상인 문서를 동시에 처리하면
- **THEN** "AI 문장 구분" 세부 진행의 끝난 줄 수는 묶음이 끝날 때마다 늘고 마지막 기록에서 전체 줄 수와 같다

### Requirement: 동시 호출 중 취소와 실패
시스템은 동시에 보내는 도중 사람이 취소하거나 한 묶음이 재시도 뒤에도 실패하면, 아직 보내지 않은 묶음은 보내지 않고 취소 또는 "처리 실패 — 다시 시도"로 멈춰야 한다(SHALL, CR-12). [제안]

#### Scenario: 한 묶음이 계속 실패
- **WHEN** 동시에 보내는 묶음 가운데 하나가 재시도 횟수를 넘겨 실패하면
- **THEN** 실행은 FAILED가 되고 남은 묶음은 보내지 않는다

#### Scenario: 동시 호출 중 취소
- **WHEN** 문장 구분 묶음을 동시에 보내는 도중 취소를 요청하면
- **THEN** 실행은 취소로 멈추고 보낸 요청 수는 전체 묶음 수보다 적다

### Requirement: AI 요청 시간 제한
시스템은 AI 요청 하나가 정해진 시간(기본 120초, 설정으로 바꿈)을 넘으면 그 요청을 실패로 보고 정해진 횟수만 다시 시도해야 한다(SHALL, CR-12). [제안]

#### Scenario: 응답이 늦은 요청
- **WHEN** 언어 모델 클라이언트를 만들면
- **THEN** 요청 시간 제한이 설정값(초)으로 걸리고, 시간 초과는 다른 오류처럼 다시 시도된다

### Requirement: 실행 목록의 결재 정보
시스템은 실행 목록의 각 줄에 그 실행의 가장 최근 상신에 대한 결재자, 상신한 사람, 상신 시각, 결정(승인·반려·없음), 결정 시각을 넣어야 한다(SHALL). 가장 최근 상신이 취소되었거나 상신한 적이 없으면 이 칸들은 비운다.

#### Scenario: 상신한 검토의 결재 정보
- **WHEN** 엔지니어가 결재자를 골라 상신한 검토가 있는 상태에서 실행 목록을 부르면
- **THEN** 그 줄에 결재자, 상신한 사람, 상신 시각이 있고 결정은 비어 있다

#### Scenario: 취소한 상신
- **WHEN** 상신을 취소한 검토가 있는 상태에서 실행 목록을 부르면
- **THEN** 그 줄의 결재 칸은 모두 비어 있다

#### Scenario: 반려된 검토
- **WHEN** 결재자가 반려한 뒤 다시 상신하지 않은 검토가 있는 상태에서 실행 목록을 부르면
- **THEN** 그 줄의 결정은 반려이고 결정 시각이 있다

### Requirement: AI 묶음 답의 줄 번호
시스템은 AI에 여러 줄을 묶어 물을 때(문장 구분·유형 붙이기·문장 초안) 답마다 묻는 글의 줄 번호를 받아 번호로 줄에 맞춰야 한다(SHALL). 번호가 빠지거나 겹치거나 범위를 벗어나면 형식 오류로 보고 같은 질문을 다시 묻지 않고, 문장 구분·유형 붙이기는 묶음을 바로 반으로 나눠 묻는다. 답의 순서가 섞여도 결과는 같다(CR-11). [제안 11-01]

#### Scenario: 순서가 섞인 답
- **WHEN** 언어 모델이 줄 번호를 붙인 답을 거꾸로 된 순서로 내면
- **THEN** 각 줄에는 자기 번호의 답이 붙고, 결과는 바른 순서로 낸 답과 같다

#### Scenario: 번호가 겹친 답
- **WHEN** 40줄 묶음에서 언어 모델이 한 번호를 빠뜨리고 다른 번호를 두 번 내 개수는 40으로 맞으면
- **THEN** 그 답은 받지 않고 같은 질문을 다시 묻지 않고 묶음을 나눠 물어, 모든 줄이 자기 번호의 답을 받는다

### Requirement: 버린 AI 설명 건수
시스템은 실행 기록 API에 검토마다 근거 대조에서 버린 위험 조건 설명 수를 함께 줘야 한다(SHALL). [제안 11-01]

#### Scenario: 버린 설명 건수
- **WHEN** 위험 조건 설명 하나가 근거에 없는 숫자로 버려진 실행을 실행 기록에서 보면
- **THEN** 그 줄의 버린 설명 수는 1이다

### Requirement: 검증 확인 필요 건수
시스템은 실행 기록 API에 검토마다 AI 검증에서 확인 필요로 표시된 위험 조건 설명 수를 함께 줘야 한다(SHALL). [제안 11-01]

#### Scenario: 검증 확인 필요 건수
- **WHEN** 위험 조건 설명 모두가 검증에서 확인 필요로 표시된 실행을 실행 기록에서 보면
- **THEN** 그 줄의 검증 확인 필요 수는 설명이 있는 위험 조건 수와 같다

### Requirement: 뜻 찾기 벡터
시스템은 분석에서 위험 조건 다음에 뜻 찾기에 쓸 글(문장 요구사항, 판정 줄 요구 원문, 항목키가 빈 표 항목 이름, 위험 표현·항목 이름 사전 표현)의 문장 벡터를 언어 모델에서 받아 글마다 저장하고, 같은 글은 다시 묻지 않아야 한다(SHALL). 언어 모델이 없으면 "뜻 찾기 안 함", 재시도 뒤에도 실패하면 "뜻 찾기 건너뜀"으로 남기고 분석은 계속해야 한다(SHALL). 벡터로는 판정·위험 조건을 만들지 않는다(MUST NOT, CR-01). [제안 11-01]

#### Scenario: 같은 글은 다시 묻지 않음
- **WHEN** 같은 문서로 검토를 두 번 돌리면
- **THEN** 두 번째 검토에서는 벡터를 묻지 않고 저장된 벡터로 같은 후보가 나온다

#### Scenario: 언어 모델 없음
- **WHEN** 언어 모델 없이 검토를 돌리면
- **THEN** 분석은 담당자 확인 단계까지 가고 뜻 찾기 상태는 "안 함", 후보는 없다

#### Scenario: 벡터 요청 실패
- **WHEN** 벡터 요청이 재시도 뒤에도 실패하면
- **THEN** 분석은 담당자 확인 단계까지 가고 뜻 찾기 상태는 "건너뜀"이다

### Requirement: AI 사용 방식 설정
시스템은 설정 하나로 AI 사용 방식을 Gemini(외부), 사내 모델(OpenAI 호환 주소), AI 끄기 가운데서 골라야 한다(SHALL). AI 끄기이면 키가 있어도 어떤 언어 모델에도 요청을 보내지 않고 코드 규칙만으로 처리해야 한다(MUST). 사내 모델이면 정한 주소로만 보내고, 벡터 모델이 정해지지 않았으면 뜻 찾기를 건너뛰어야 한다(SHALL). 모델이 바뀌면 처리 판이 달라져 같은 파일도 새로 분석한다(NFR-02). [제안 11-01, C5]

#### Scenario: AI 끄기
- **WHEN** Gemini 키가 있고 방식이 AI 끄기인 상태에서 검토를 돌리면
- **THEN** 언어 모델 요청은 0건이고 검토는 규칙만으로 담당자 확인 단계까지 가며 실행 기록의 모델은 비어 있다

#### Scenario: 사내 모델로 보냄
- **WHEN** 방식이 사내 모델이고 주소와 모델이 정해진 상태에서 검토를 돌리면
- **THEN** 언어 모델 요청은 모두 그 주소로 가고 실행 기록의 모델은 사내 모델 이름이다

#### Scenario: 사내 모델 설정 오류
- **WHEN** 사내 모델 주소가 키 오류(401)나 모델 없음(404)으로 답하면
- **THEN** 다시 묻지 않고 "AI 키 또는 모델 설정 오류 — 설정 확인"으로 멈춘다

#### Scenario: 사내 벡터 모델 없음
- **WHEN** 방식이 사내 모델이고 벡터 모델이 정해지지 않은 상태에서 검토를 돌리면
- **THEN** 뜻 찾기 상태는 "건너뜀"이고 분석은 담당자 확인 단계까지 간다

### Requirement: 실행 기록의 이어서 시작한 단계
시스템은 실행 기록 응답에 이어서 다시 시도한 검토의 이어서 시작한 단계 이름을 돌려주고, 처음부터 돌린 검토는 비워 두어야 한다(SHALL). [제안 11-01, C2]

#### Scenario: 처음부터 돈 검토
- **WHEN** 한 번에 끝난 검토의 실행 기록을 부르면
- **THEN** 이어서 시작한 단계가 비어 있다

### Requirement: 다시 처리한 문서 수
시스템은 실행 기록 응답에 그 검토에서 점검 때문에 AI에 다시 물은 문서 수와 다시 물은 줄 수를 돌려주어야 한다(SHALL). 점검에 걸렸어도 다시 묻지 않은 문서는 세지 않는다. [제안 11-01, C1] [다시 물은 줄 수: 제안 11-02]

#### Scenario: 다시 처리한 문서가 있는 검토
- **WHEN** 문서 하나를 점검 뒤 일부 줄만 다시 물은 검토의 실행 기록을 부르면
- **THEN** 다시 처리한 문서 수가 1이고 다시 물은 줄 수가 그 문서에 남은 줄 수와 같다

#### Scenario: 다시 묻지 않은 점검
- **WHEN** 표 칸 요구값이 없는 입찰 서식 하나만 점검에 걸린 검토의 실행 기록을 부르면
- **THEN** 다시 처리한 문서 수와 다시 물은 줄 수가 모두 0이다

### Requirement: 문서 추가 개정 결과
시스템은 검토에 문서를 더해 다시 판정하면 개정 결과(개정 번호, 더한 파일 이름, 다시 판정한 시각, 판정 값이 바뀐 줄 수, 새로 생긴 줄 수, 사라진 줄 수)를 남기고 실행 요약·실행 목록에 내야 한다(SHALL). 같은 줄은 요구값·비교 제품·비교 규칙이 같은 판정이다. 판정 줄마다 마지막 개정에서 바뀜·추가 여부를 내고, 바뀌거나 추가된 줄만 거를 수 있어야 한다(SHALL). 문서를 더하지 않은 검토와 비교 제품을 바꿔 다시 판정한 결과는 개정이 아니다. [제안] 값이 바뀐 같은 항목은 사라짐 1·추가 1로 센다.

#### Scenario: 개정 결과 줄 수
- **WHEN** 담당자 확인 단계 검토에 addendum_gis.docx를 더해 다시 분석이 끝나면
- **THEN** 실행 요약과 실행 목록에 개정 1, 파일 이름 addendum_gis.docx, 새로 생긴 줄 수가 보이고, 새로 생긴 줄 수는 늘어난 판정 줄 수와 사라진 줄 수의 합과 같다

#### Scenario: 바뀐 줄만 보기
- **WHEN** 처음 분석과 판정 값이 다른 같은 줄이 하나 생긴 상태로 바뀐 줄만 거르면
- **THEN** 그 줄은 "바뀜"이고 새 줄은 "추가"이며, 거른 목록에는 바뀜·추가 줄만 있다

#### Scenario: 문서를 더하지 않은 검토
- **WHEN** 문서를 더하지 않고 분석을 마친 검토를 보면
- **THEN** 개정 결과가 없고 판정 줄에 개정 표시가 없으며 바뀐 줄만 거르면 0줄이다

### Requirement: 흐름 기록 응답
시스템은 검토 하나의 저장된 흐름 기록을 단계 순서대로 돌려주어야 한다(SHALL). 단계마다 단계 이름, 끝난 시각, 걸린 시간, 바뀐 값(건수의 전과 후), 그 단계에서 받은 사람 동작을 내고, 마지막에 흐름이 멈춘 자리(사람 단계 이름, 처리 중간이면 다음 단계, 끝)를 낸다. 흐름 기록을 불러도 흐름과 검토 단계는 바뀌지 않는다(읽기 전용). 흐름 기록이 없는 검토는 빈 목록과 기록 없음을 낸다. [제안 11-02, C2]

#### Scenario: 담당자 확인까지 처리한 검토
- **WHEN** 담당자 확인에서 멈춘 검토의 흐름 기록을 부르면
- **THEN** 문서 처리부터 담당자 배정까지 단계가 순서대로 오고 판정 단계에 판정 수가 0에서 그 검토의 판정 수로 바뀐 값이 있으며, 멈춘 자리는 담당자 확인이고 검토 단계는 그대로다

#### Scenario: 상신한 검토
- **WHEN** 결재를 상신한 검토의 흐름 기록을 부르면
- **THEN** 담당자 확인 단계에 사람 동작 "상신"이 남고 멈춘 자리는 승인 대기다

#### Scenario: 흐름 기록이 없는 검토
- **WHEN** 흐름 기록이 없는 검토의 흐름 기록을 부르면
- **THEN** 단계 목록이 비어 있고 기록 없음이다

### Requirement: 빈 마감 채우기 명령
시스템은 사람이 개발·시연 DB에서 돌리는 명령으로만 마감일이 빈 검토의 마감을 시작일 + 정한 날 수로 채우고, 검토마다 이력(이전 값, 새 값, 사유 "시연 데이터 마감 채움")을 남겨야 한다(SHALL). 마감이 있는 검토는 바꾸지 않는다. 시스템이 저절로 채우지 않는다(CR-04).

#### Scenario: 빈 마감 채우기
- **WHEN** 마감이 빈 검토와 마감이 있는 검토가 있는 DB에서 날 수 14로 명령을 돌리면
- **THEN** 빈 검토의 마감은 시작일 + 14일이 되고 이력 1건이 남으며, 마감이 있던 검토는 그대로다

### Requirement: 분석 밖 AI 사용량 기록
시스템은 분석 실행 밖에서 AI를 부른 요청(검토 도우미 질문, 협조 요청 확인할 점, 비교 제품 바꾸기·손실값 고치기·판정 확정 뒤 다시 만들기)마다 기능·검토·모델·호출 수·재시도·토큰을 남겨야 하고, AI를 부르지 않은 요청은 남기지 않아야 한다(SHALL). 날짜·기능별 사용량과 추정 비용(팀 가정 단가)을 분석 실행 사용량과 함께 돌려줘야 한다(SHALL). [제안 11-03]

#### Scenario: 검토 도우미 사용량
- **WHEN** AI가 켜진 상태에서 검토 도우미에 질문하면
- **THEN** 사용량에 검토 도우미 한 줄(그 검토, 호출 수, 토큰)이 남는다

#### Scenario: AI를 부르지 않은 요청
- **WHEN** AI가 꺼진 상태에서 검토 도우미에 질문하면
- **THEN** 사용량은 남지 않는다

#### Scenario: 날짜·기능별 사용량
- **WHEN** 같은 날 검토 도우미 질문 2번과 AI를 쓴 분석 1건이 있으면
- **THEN** 사용량 응답에 그날 검토 도우미(호출 합)와 분석 줄이 따로 있고, 합계에 추정 비용이 있다
