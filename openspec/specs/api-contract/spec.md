# api-contract Specification

## Purpose
화면과 서버가 주고받는 API 응답의 모양을 정해 공개하고, 그 모양을 벗어난 값이나 원문 위치가 없는 근거 값이 화면이나 내보내기로 나가지 않게 한다.

## Requirements

### Requirement: 응답 스키마 공개
시스템은 JSON을 돌려주는 모든 API의 응답 모양(칸 이름, 값 형식, 빈 값 허용 여부, 정해진 값 목록)을 `/openapi.json`에 공개해야 한다(SHALL). 파일을 돌려주는 API는 JSON 모양 대신 파일 형식을 밝혀야 한다(SHALL).

#### Scenario: 판정 목록의 응답 모양
- **WHEN** `/openapi.json`을 조회하면
- **THEN** 판정 목록 API의 성공 응답에 판정 칸(판정 번호, 요구사항 번호, 결과, 가정 여부, 원문 위치 등)과 각 칸의 형식이 있다

#### Scenario: 파일 내려받기 API
- **WHEN** `/openapi.json`에서 TBE 준수표 내려받기 API를 보면
- **THEN** 성공 응답은 엑셀 파일 형식으로 적혀 있고 JSON 모양은 없다

### Requirement: 응답 검사
시스템은 응답을 보내기 전에 공개한 모양으로 검사하고, 맞지 않는 응답은 보내지 않고 오류로 기록해야 한다(SHALL). 모양에 없는 칸을 새로 만들거나 빈 칸을 기본값으로 채우지 않아야 한다(MUST NOT, CR-04).

#### Scenario: 정해진 값 밖의 판정 결과
- **WHEN** 판정 줄의 결과 값이 정해진 값(준수, 일탈 후보, 질의 후보, 확인 필요, 작성 필요) 밖이면
- **THEN** 판정 목록 API는 그 응답을 보내지 않고 서버 오류를 돌려주며 원인을 기록한다

#### Scenario: 비어 있는 값
- **WHEN** 판정의 제품 값이 비어 있으면
- **THEN** 응답에서 그 칸은 빈 값으로 오고 0이나 다른 값으로 채워지지 않는다

### Requirement: 근거 응답의 원문 위치
시스템은 판정, 보증값 후보, 손실 환산, 공학 검산, 일탈·질의 항목, 제안 포인트 응답의 줄마다 원문 위치를 하나 이상 담아야 하고, 각 위치에는 파일 번호가 있어야 한다(SHALL, CR-02·03). 위치가 없는 줄은 응답에 넣지 않아야 한다(MUST NOT). 가정 여부 칸은 이 응답들에서 빠지면 안 된다(MUST NOT, CR-06).

#### Scenario: 위치가 없는 판정
- **WHEN** 원문 위치를 찾지 못한 판정이 있는 실행의 판정 목록을 조회하면
- **THEN** 그 판정은 목록에 없고, 목록의 모든 줄에 파일 번호가 있는 위치가 하나 이상 있다

#### Scenario: 팀 가정 표시가 함께 감
- **WHEN** 팀 가정 손실값으로 계산한 손실 환산을 조회하면
- **THEN** 응답 줄에 가정 여부가 참으로 있다

### Requirement: 화면 타입과 서버 스키마 일치
화면이 쓰는 응답 타입은 공개한 서버 스키마에서 만들어야 하고(SHALL), 자동 검사는 서버 스키마로 다시 만든 타입이 저장소의 타입과 다르면 실패해야 한다(SHALL).

#### Scenario: 서버 칸을 바꾸고 타입을 다시 만들지 않음
- **WHEN** 응답 모델에 칸을 더하고 화면 타입을 다시 만들지 않은 채 자동 검사를 돌리면
- **THEN** 검사가 실패하고 다른 타입 파일 이름을 알려 준다

#### Scenario: 화면이 없는 칸을 씀
- **WHEN** 화면 코드가 서버 스키마에 없는 응답 칸을 읽으면
- **THEN** 프런트 빌드(타입 검사)가 실패한다
