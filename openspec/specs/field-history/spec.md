# field-history Specification

## Purpose
RFP 요구가 우리 제품군의 실제 현장 고장과 이어질 때, 팀이 확정한 요구–고장 연결표만 조회해서 "우리는 이 조건이 왜 중요한지 겪어서 안다"는 근거를 제안 포인트 후보로 붙인다 (FR-15).

## Requirements

### Requirement: 연결표 조회로만 잇기
시스템은 검토 실행에서 요구–고장 연결표를 조회만 해서(코드) 요구사항과 고장 사전의 고장을 이어야 한다(SHALL). 요구 원문에 연결표 항목키의 같은 뜻 표현이 있고 그 요구의 설비 종류가 연결표 줄의 적용 설비에 들 때만 잇는다. AI가 즉석에서 짝을 짓지 않아야 한다(MUST NOT).

#### Scenario: 결로 방지 히터
- **WHEN** 요구 항목 "결로 방지 히터"(파일 4 RFP04 GIS Specification 고압 개폐기 사양서 327행)가 있고 연결표에 결로 방지 히터–MV_EQUIP–FLT-051 줄이 있으면
- **THEN** FLT-051(결로 방지 히터 꺼짐 → 결로 → 부분방전 경보)을 잇는다

#### Scenario: 연결표에 없는 항목
- **WHEN** 요구 항목이 연결표에 없으면
- **THEN** 연결하지 않는다

#### Scenario: 설비 종류가 다름
- **WHEN** 같은 뜻 표현이 있지만 요구의 설비 종류가 연결표 줄의 적용 설비에 없으면(변압기 함의 히터 ↔ 개폐기 고장)
- **THEN** 연결하지 않는다

### Requirement: 현장 경험 후보
시스템은 이어진 연결표 줄마다 한 실행에 현장 경험 제안 포인트 후보 하나를 만들어야 한다(SHALL). 근거는 대표 요구의 원문 위치와 연결표 줄(고장 번호)이고, 근거 칸에 같은 요구 수와 파일 번호를 적는다. 후보는 엔지니어가 채택·버림·수정한다 (CR-08).

#### Scenario: 같은 고장이 여러 요구에
- **WHEN** 같은 연결표 줄에 이어지는 요구가 여러 파일에 있으면
- **THEN** 후보는 하나이고, 파일 번호·행이 가장 앞선 요구를 대표로 두고 근거 칸에 요구 수를 적는다

### Requirement: 고장 사전 내용만으로 쓴 문장
시스템은 현장 경험 후보의 문장을 고장 사전의 증상·원인·조치와 해결 사례 수만으로 코드가 써야 하고(SHALL), 그 밖의 내용을 넣지 않아야 한다(MUST NOT). 고장 번호와 건수는 자리표시자로 채운 뒤 근거 값과 대조한다 (CR-07). 언어 모델에는 보내지 않는다.

#### Scenario: 문장 내용
- **WHEN** FLT-051 후보를 만들면
- **THEN** 문장에는 FLT-051의 증상·원인·조치와 의심 사례를 뺀 해결 사례 수 외 내용이 없다

#### Scenario: 언어 모델이 있어도
- **WHEN** 언어 모델이 연결되어 있으면
- **THEN** 현장 경험 문장은 코드가 쓰고 언어 모델에 보내지 않는다

### Requirement: 의심 사례를 뺀 해결 사례 수
시스템은 해결 사례 수를 셀 때 의심 사례를 빼야 하고(MUST), 뺀 수를 근거 칸에 적는다. [결정] 2026-10-23 팀

#### Scenario: 의심 사례
- **WHEN** FLT-051 해결 사례 5건 중 1건이 의심 사례이면
- **THEN** 해결 사례 수는 4건이고 근거 칸에 "의심 사례 1건 제외"를 적는다

### Requirement: 데이터가 없으면 꺼 둠
시스템은 고장 사전이 적재되지 않았으면 현장 이력을 잇지 않아야 한다(MUST NOT). [결정] Q8: 프로젝트 1 데이터 사용 허용 (2026-10-23)

#### Scenario: 고장 사전 파일 없음
- **WHEN** 고장 사전 파일 없이 규칙 사전을 적재하면
- **THEN** 연결표가 비고 현장 경험 후보를 만들지 않는다
