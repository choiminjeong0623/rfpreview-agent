# 문서 종류별 처리기, 처리 뒤 점검, 문서 병렬 처리 (C조 C1)

## 왜

- 지금은 문서 종류(입찰 서식·요구 사양·시험 사양·구매 사양·공급사 사양)를 알아내도 처리는 모두 같다. AI에 문장 구분·유형을 물을 때도 어떤 종류의 문서인지 알려 주지 않는다.
- 처리 결과가 문서 종류와 맞지 않아도(예: 입찰 서식인데 표 칸 요구값이 하나도 없음) 아무도 모른다. 잘못 분류된 문서가 그대로 지나간다.
- 한 검토의 문서를 하나씩 차례로 처리한다. 문서가 여러 개면 그만큼 기다린다.
- AI 기술 활용성 자체 평가의 "여러 에이전트 구조" 추천(검증 에이전트 다음 문서 종류별 추출 + 병렬)의 나머지다. 발표에서는 "에이전트" 대신 "문서 종류별 처리기(코드 규칙 + AI 보조)"라고 부른다.

## 무엇

- **처리기 표(코드)**: 문서 종류마다 처리기 하나. 처리기가 정하는 것은 두 가지다.
  - AI 문장 구분·유형 질문 앞에 넣는 문서 종류 설명 한 줄. 프롬프트 판 p5(같은 파일도 새로 분석).
  - 처리 뒤 점검 기준. 입찰 서식은 표 칸 요구값, 요구 사양·구매 사양은 요구사항 줄, 시험 사양은 시험 유형 줄, 공급사 사양은 C/D/E 표시가 하나도 없으면 걸린다. 종류 모름은 점검하지 않는다.
- 추출 규칙(표·문장·값·위험 표현)은 모든 종류가 같다. 처리기는 판정·후보를 고르지 않는다(CR-01).
- **점검 뒤 한 번 다시 처리**: 점검에 걸리면 종류 설명이 없는 일반 처리기로 그 문서를 한 번만 다시 처리한다(틀린 종류 설명이 AI를 잘못 이끌었을 수 있어서). AI가 없으면 다시 처리하지 않는다. 어느 쪽이든 걸린 이유를 문서에 남기고 "확인 필요"로 둔다.
- **문서 병렬 처리**: 한 검토의 문서를 정해진 개수(기본 2, `RFP_DOC_WORKERS`)만큼 동시에 처리한다. 구조·추출·AI 질문은 동시에 하고 저장은 올린 순서대로 해서, 같은 요구 묶기(dedup)·파일 번호·결과는 차례로 처리할 때와 같다(CR-11).
- 문서 표 응답에 처리기·점검 결과·다시 처리 여부, 실행 기록에 "다시 처리한 문서 n"을 더한다(화면 표시는 v4.96 화면 작업에서).

## 하지 않음

- 종류마다 다른 추출 규칙(K1·K2를 다시 재야 해서 이번에는 하지 않음, minjeong 결정 11-01).
- 점검에 걸린 문서의 종류를 코드가 바꾸기. 종류는 사람이 고친다.
- 문서 하나 안의 처리를 더 쪼개 병렬로(이미 AI 묶음은 동시에 묻는다, NFR-10).

관련: 명세서 FR-01 ④ "문서 종류별 처리기 [C1]", NFR-10 "문서 병렬 처리 [C1]", 기획서 6장 문서 분류.
