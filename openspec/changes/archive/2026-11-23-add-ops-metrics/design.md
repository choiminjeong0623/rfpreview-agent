# Design: add-ops-metrics

## D1. 역할별 AI 호출 지표는 기록에서 코드로 계산 (P1-1)

`ai_call`에는 요청 번호가 없고 시도마다 한 줄이다(`attempt` 0 = 첫 시도). 요청은 호출 순서(`call_id`)로 읽으며 `attempt = 0`이면 새 요청을 열고, `attempt > 0`이면 같은 `input_hash`로 열린 가장 최근 요청에 붙인다(재시도는 같은 프롬프트를 다시 보낸다). 동시 호출로 줄이 섞여도 입력 해시로 맞춘다.

- p50·p95: 시도마다의 `duration_ms`를 가까운 순위(nearest rank)로. 모델 비교의 `nearest_rank`와 같은 함수.
- 실패율: 성공(`OK`)이 아닌 시도 / 시도.
- 버린 비율: 성공한 시도 중 `dropped_reason`이 있는 것 / 성공한 시도.
- 재시도 뒤 성공: 첫 시도가 성공이 아니고 나중 시도 중 하나가 성공한 요청 수.

SQL 집계(percentile_cont) 대신 파이썬으로 한 이유: 모델 비교와 같은 백분위 정의를 쓰고, 요청 묶기가 SQL로는 읽기 어렵다. 한 검토의 호출은 수천 건 이하라 메모리로 충분하다.

## D2. 평가 중 비용 상한 (P1-5)

`evaluate`가 문항마다 묻기 전에 `usage.minus(before)`로 지금까지 쓴 비용을 단가표로 계산하고, 멈출 값을 넘었으면 묻지 않고 `Answer(None, error="BUDGET")`를 돌려준다. 문항은 동시에 묻기 때문에 이미 시작한 문항(최대 동시 수)은 끝까지 간다. 그래서 멈출 값을 조금 넘을 수 있고, 이유에 실제 쓴 비용을 적는다.

- 멈출 값: 확인 옵션 없음 → 상한. 확인 옵션(`--yes`, 모델 비교) → max(상한, 어림 × 2). 확인은 "어림만큼은 써도 된다"는 뜻이라 어림이 두 배 넘게 틀렸을 때만 멈춘다.
- 결과: `status = FAILED`, `skip_reason = "비용 상한 N원을 넘어 멈췄습니다 (쓴 비용 약 M원, 묻지 않은 문항 k개)"`. 기존 소비자(CLI·화면 평가·Langfuse 기록)는 `DONE`일 때만 비교·기준선·올리기를 하므로 따로 막을 곳이 없다. 마이그레이션 없음(`FAILED`는 이미 있는 상태).
- 버린 대안: 반복 사이에서만 확인 — 1번 반복 평가에서는 소용이 없다.

## D3. 사람 수정 비율 (P1-8)

분자: 현재 판정 중 `review_status IN ('EDITED','REJECTED')`. 분모: 분자 + 한 줄씩 확정(`CONFIRMED`이면서 마지막 확정 이력이 한꺼번에 확정이 아님).

한꺼번에 확정 구분: 마이그레이션 없이 `bulk_confirm`이 이력 이유 칸에 `"한꺼번에 확정"`을 남긴다. 예전 이력은 표시가 없어서, 같은 검토·같은 사람·같은 `acted_at`(한 트랜잭션의 `now()`)에 확정 이력이 둘 이상이면 한꺼번에 확정으로 본다. 한 줄씩 확정은 요청마다 트랜잭션이 달라 시각이 겹치지 않는다.

지표 코드는 `EDIT-RATE`, 목표 없음(`target = None`), 낮을수록 좋음. 95 % 구간은 다른 비율 지표처럼 붙는다.
