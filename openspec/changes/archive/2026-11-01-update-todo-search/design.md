# Design

## 결정

### 1. 거르기는 화면에서, 서버는 모든 부서를 한 번에

요청은 검토마다 수십 건이라 전부 받아도 가볍다. `GET /assignments`(role 생략)를 한 번 불러 탭 건수·검색 영역 목록·RFP별 묶음을 모두 화면에서 만든다. 사업 → RFP 검토 목록 좁히기, 조건 칩 풀기처럼 자주 바뀌는 거르기를 서버 왕복 없이 한다. 검색어는 요구사항 문장·원문 위치·보낸 주소·검토 번호·검토 이름에서 대소문자 없이 찾는다.

### 2. 회신 상태

| 회신 거르기 | 뜻 |
|---|---|
| 회신 대기 | 메일 보냄, 회신 기한(보낸 날 + 3일) 안 |
| 회신 기한 지남 | 메일 보냄, 회신 기한 지남 |
| 회신 받음 | 회신 받음 |

요약 줄(안 보냄·회신 대기·24시간 넘게 회신 없음·회신 받음)은 지금 상태 그대로 세고, 누르면 그 상태만 거른다(다시 누르면 풂). 24시간과 3일 기한은 따로다: 24시간은 "다시 연락 필요" 알림, 3일은 회신 기한.

### 3. 재요청은 같은 보내기 API에 `resend`

새 API 대신 `POST /runs/{id}/assignments/send`에 `resend`를 더한다. `resend`면 메일 보냄인 요청도 보낼 대상이 되고(회신 받음은 아님), 메일은 지금과 같은 모양(제목·본문·엑셀)으로 다시 나간다. 보낸 시각·보낸 사람이 바뀌고 이력에 `SEND`(after_value `resend: true`)로 남는다. `repeat_count`는 "같은 조건 n곳"이라 건드리지 않는다. 재요청 횟수를 저장하는 칸은 만들지 않는다(이력으로 셈).
10-31 결정 "재요청 자동 알림 없음"은 그대로다: 자동으로는 한 번만, 사람이 누를 때만 다시.

### 4. 내보내기는 화면이 고른 id로

화면이 거른 결과를 서버가 다시 거르지 않게 `POST /assignments/export`에 화면이 보이는 요청 id를 보낸다(쪽 나누기 없이 거른 전부). 서버는 그 id 가운데 원문 위치가 있는 요청만, 화면과 같은 순서로 쓴다. 상태 이름은 서버가 내보내는 시각 기준으로 정한다. GET 쿼리에 id 수천 개를 넣지 않으려고 POST다(화면 명세의 예정 API `GET /assignments/export`를 바꿈).

### 5. CSS와 쪽 크기

v4.96 Todo CSS에서 새로 쓰인 규칙(`.fbar` `.ff` `.fbar2` `.fchips` `.fchip` `.sumline button` `.rpl` `.mk` `.emp` `.sech .seg` `.rgs` `.rg*` `.dpt`)만 원본 그대로 `mockup/TodoV496.css`에 옮긴다(AI 요약 `.ais*`와 글꼴 정의는 뺌). 표는 목업처럼 5줄씩 시작하고 5·10·20을 고른다(`Pager`에 쪽 크기 목록을 받게 함).

## 위험

- 요청이 수천 건이 되면 한 번에 받는 응답이 커진다 → 지금 규모(검토 수십 건)에서는 문제 없다. 커지면 서버 거르기로 옮긴다.
