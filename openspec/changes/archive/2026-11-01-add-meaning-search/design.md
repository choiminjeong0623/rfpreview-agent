# 설계

## 벡터

- `GeminiLLM.embed(texts)`: `gemini-embedding-001`, 768차원(`output_dimensionality`), 한 번에 100개. 재시도·오류 종류는 `call_with_retry`와 같은 규칙(`embed_with_retry`).
- `text_vector(model, text_hash, vec REAL[])`: 글자(normalize 전 원문 공백 정리)의 sha256. 같은 글은 다시 묻지 않는다(다른 검토·다시 시도 포함).
- 코사인은 파이썬. 검토당 대상은 수천 개라 numpy 없이 충분.
- 테스트는 FakeLLM.embed(단어 해시 벡터, 또는 글별로 정한 벡터).

## 분석 단계

- `meaning` 단계(위험 조건 뒤, 목록 앞): 대상 글 = (B5) 출처가 문장인 요구사항, 사전 표현, (B4) 판정 줄의 요구 원문, (B3) 판정 대상 문서에서 항목키가 빈 표 항목 이름과 항목 이름 사전 표현. 벡터를 받고 B3·B5 후보를 `meaning_candidate`에 저장한다.
- 상태는 `review_run.graph_state.meaning`: DONE / NO_AI(언어 모델 없음) / SKIPPED(실패). 실패는 분석을 멈추지 않는다(뜻 찾기는 힌트라 CR-12의 "멈춤"보다 계속이 낫다). 키·모델 설정 오류도 SKIPPED.
- 같은 입력·같은 벡터면 같은 후보(CR-11). 후보 순서는 점수 내림차순, 같으면 요구사항 번호.

## B3 항목 연결 후보

- 표 항목 이름(`table_row.item_name_raw`) 중, 그 줄 값의 `item_key`가 비어 있고 판정 대상 문서(묶음 A·B)인 것. 같은 이름은 한 번.
- 항목 점수 = 그 항목의 표현(사전 "같은 뜻의 원문 표현"과 한글 이름) 중 최대 코사인. 1등 ≥ 0.85, 1등 − 2등 ≥ 0.03.
- 실험(실제 Gemini): "Rated lightning impulse withstand voltage" ↔ "(Up)" 표기 0.907, ↔ "power-frequency withstand voltage" 0.807. 그래서 문턱이 높고 차이 조건이 있다.
- 판정 규칙 화면에서 [같은 뜻 표현으로 추가] = 기존 규칙 고치기 API로 그 항목의 표현에 덧붙임(고침 이력). [숨기기] = 후보 상태 HIDDEN. 이미 사전에 들어간 이름은 목록에서 빠진다.

## B4 뜻이 비슷한 지난 확정

- `review_memory.hints`: 글자 열쇠가 없을 때만. 다른 검토의 사람 판정 중 요구값 원문(normalize)·비교 제품이 같고, 두 요구 원문 벡터가 모두 저장돼 있고, 코사인 ≥ 0.92인 것 중 점수가 가장 높은 것(같으면 최근). 힌트에 `match`(TEXT/MEANING), `score`.
- 화면에서 묻는 동안 AI를 부르지 않는다(저장된 벡터만).

## B5 사전 추가 후보

- 비교 대상 = 이 검토의 포괄 조항·범위 모호 위험 조건 구성 문장 + 위험 표현 사전 표현. 지난 검토 문장은 쓰지 않는다(같은 입력 같은 결과).
- 대상 = 이 검토 문서의 문장 요구사항 중 어떤 위험 조건에도 들지 않은 것. 최대 코사인 ≥ 0.72, 많아야 20개.
- 실험: "deemed to be accepted" 문장 ↔ "considered as fully complied with" 문장 0.767, 관계없는 문장 0.55~0.59.

## 대안

- pgvector: CI·도커 이미지 바꿈. 지금 크기에 필요 없음.
- AI에게 바로 "비슷한가" 묻기: 비용·시간이 크고 점수를 코드로 다루기 어려움.
