# Design

## Context

스키마 v1에 assignment(담당 역할, 요구사항 또는 제안 포인트, 반복 수, 상태)가 있다. 유형 → 담당 규칙은
requirement_type.default_role(명세서 2-2). 로그인은 없고 화면에서 사용자를 고른다(app_user).

## Decisions

### 1. 보내는 대상
- 주 유형(is_primary)의 담당 역할이 견적·품질·영업인 요구사항만 보낸다. 기술 검토 엔지니어 몫(기술 성능·위험 조건·
  규격·설치 환경)과 미분류는 검토 화면에서 이미 보므로 할 일을 만들지 않는다 (명세서 ⑤).
- 원문 위치가 없는 요구사항은 보내지 않는다 (CR-02). 다른 문서에 같은 줄이 있어 대표가 이 실행에 있으면 대표만 본다.
- 실행 단계(처리 중·실패)를 지난 검토의 할 일만 화면에 보인다.

### 2. 반복 조건 묶기
- 같은 담당 역할에서 "같은 조건 글"이 같으면 한 건. 표 행은 항목 이름(목록 표시·끝 문장부호 뺌) + 요구값, 문장은 목록
  표시를 뺀 문장. 공백·대소문자를 맞춘다. 번호·단위 칸은 보지 않는다.
- 대표는 문서 순서상 첫 줄, 묶인 요구사항 id와 위치는 모두 남긴다. 반복 수 = 묶인 줄 수.
- 대안: 항목 키(item_key)로 묶기 → 제조사 자격·시험 줄은 대부분 항목 키가 없어 묶이지 않는다.

### 3. 제안 포인트
- 채택·고쳐서 채택한 포인트만 (AR-08). 여유·현장 이력 → 영업, 손실 환산 → 영업과 견적 (명세서 ④ "영업·견적에 전달").
- 엔지니어가 채택·버림을 바꿀 때마다(확인 동작 뒤) 할 일을 다시 만든다. 손실값 고치기 뒤에도 다시 만든다.

### 4. 상태 이어 쓰기
- 할 일 키: 요구사항은 "R|역할|같은 조건 글", 포인트는 "P|역할|종류|요구 id|근거". 다시 만들 때 같은 키면 상태·처리한
  사람·보낸 시각을 이어 쓴다.
- 제안 포인트는 다시 만들 때 지우고 새로 넣으므로 point_id 외래 키를 ON DELETE SET NULL로 바꾸고 "요구사항 또는 포인트
  하나" 검사를 "많아야 하나"로 푼다. 바로 뒤 전달 단계가 새 포인트를 가리키게 다시 만든다. 그 사이 빈 행은 화면에 내지 않는다.
- 상태는 그 역할 사용자만 바꾼다 (다른 역할 403, 없는 상태 400, 없는 할 일 404).

### 5. "내 할 일" 화면
- 머리말에 "검토 / 내 할 일" 전환. 고른 사용자 역할로 내용이 바뀐다.
- 견적·품질·영업: 할 일 카드(유형 또는 제안 포인트 종류, 반복 배지, 원문, 원문 위치, 상태 버튼). 끝난 일은 기본으로 숨긴다.
- 엔지니어: 담당자 확인 중인 검토 카드(요약 수, 지금 걸리는 승인 기준). 승인자: 승인 대기 검토 카드(승인 사유).
  카드를 누르면 그 검토를 연다 (승인자는 승인 탭).

## Risks / Trade-offs

- 같은 조건 글이 조금만 달라도(띄어쓰기 외 철자) 따로 나간다 → 반복 수가 크게 줄어드는 정도로 충분하다고 본다. [제안]
- 메일·알림으로 보내지는 않는다. 전달 기록은 화면의 "내 할 일"이다.
