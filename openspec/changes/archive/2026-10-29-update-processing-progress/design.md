# Design

## 결정

1. **세부 진행은 별도 연결로 바로 저장한다.** 문서 하나의 처리는 한 트랜잭션 안에서 돈다(`process_document`의 `conn.transaction()`).
   같은 연결로 진행을 적으면 끝날 때까지 다른 화면에서 보이지 않는다. 그래서 `RunContext.progress`에 진행 기록 함수를 두고,
   API 백그라운드 실행(`service.run_to_end`)은 자동 커밋 연결을 하나 더 열어 `review_run.graph_state.detail`만 바꾼다.
   이 갱신은 키가 아닌 칸만 바꾸므로 본 트랜잭션의 `run_document` 외래 키 잠금과 부딪히지 않는다. 진행 함수가 없으면(테스트, CLI) 아무것도 적지 않는다.
2. **AI 일은 묶음(40줄)마다 진행을 알린다.** `tasks.label_sentences`, `tasks.type_unclassified`가 `on_progress(끝난 줄, 전체 줄)`을 받는다.
   절마다 나눠 부르는 문장 구분은 문서 전체 문장 수를 전체로 삼아 이어 센다.
3. **`graph_state` 모양:** `{"step": ..., "detail": {"part", "done", "total", "file_index", "file_count"} | null, "updated_at": ISO 시각}`.
   단계가 바뀌면 `detail`을 지우고 `updated_at`을 새로 적는다. 응답은 `step_detail`(없으면 null)과 `step_updated_at`.
4. **막대 비율은 화면이 정한다 [제안].** 문서 읽기 단계가 2~85%, 나머지 9단계가 85~99%를 나눈다. 문서 읽기 안에서는 파일 순번으로 나누고,
   한 파일 안에서 종류 확인 0, 절·표 2%, 뽑기 5%, AI 문장 구분 5~20%, 저장 20~25%, AI 유형 붙이기 25~100%로 센다.
   비율은 2026-10-25 실측(유형 붙이기가 AI 비용의 약 90%)에 맞춘 어림값이다. 백분율은 진행이 거꾸로 가지 않는다(같은 단계 안에서 커지기만 한다).
5. **멈춤 안내:** 마지막 진행 시각이 10분 넘게 지났으면 "10분 넘게 진행이 없습니다. 백엔드가 꺼졌다면 검토를 다시 등록해 주세요."를 보인다.
   AI 한 묶음은 보통 10초 안팎이라 10분이면 충분히 길다 [제안].
6. **목록 새로고침:** 검토 목록·홈은 처리 중인 실행이 하나라도 있으면 5초마다 실행 목록을 다시 부른다. 처리 중인 실행이 없어지면 멈춘다.

## 대안

- 로그에 진행을 찍기: 사용자가 터미널을 봐야 해서 화면 문제를 풀지 못한다.
- 서버가 백분율을 계산해 주기: 단계 가중치는 화면 표시 문제라 화면에 둔다. 서버는 사실(어느 일, 몇 줄 중 몇 줄)만 준다.
- 시간 기반 가짜 진행 막대: 실제로 멈춰도 막대가 움직여 멈춤을 숨긴다. 쓰지 않는다.

## 위험

- 별도 연결 하나가 실행 동안 열려 있다. 실행이 많지 않은 MVP에서는 문제없다.
- 진행 기록 실패가 처리 실패가 되면 안 된다. 기록 함수는 예외를 삼키고 경고만 남긴다.
