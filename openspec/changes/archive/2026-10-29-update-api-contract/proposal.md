# Proposal

## Why

화면과 서버가 주고받는 응답의 모양이 어디에도 정해져 있지 않다. API 52개 중 응답 스키마가 있는 것은 `/api/health` 하나뿐이고,
나머지는 DB에서 읽은 dict를 그대로 돌려준다(`api/runs.py`, `api/reference.py`의 `-> dict`, `-> list[dict]`). 그래서 `/openapi.json`에도 응답 칸이 없다.
화면 타입(`frontend/src/api.ts`)은 사람이 손으로 맞춘 것이고, 받은 JSON을 검사 없이 그 타입으로 믿는다(`call<T>`).

이미 어긋난 곳이 있다. 예를 들어 화면의 `Requirement` 타입에는 `file_name`이 있지만 요구사항 목록 API는 그 칸을 보내지 않는다.
반대로 API가 보내는 `req_kind`(요구사항·작성 규칙·설명)는 화면 타입에 없다. 어긋나도 테스트와 빌드는 통과하고, 화면에는 빈칸이 조용히 보인다.

이 시스템에서는 이것이 검증 문제다. 판정·일탈·질의·보증값은 원문 위치가 있어야만 내보낼 수 있다(CR-02·03).
지금은 그 규칙을 조회 코드(`_with_locations`)가 지키고 있지만, 응답 모양으로는 보장하지 않는다. 누가 조회를 고치다 위치를 빠뜨려도 막을 곳이 없다.

관련: CR-02·03(근거 위치), CR-04(빈 값은 비움), CR-06(팀 가정 표시), CR-08(후보), CR-11(같은 입력 같은 결과).
2026-10-29 minjeong: "pydantic으로 API에 응답 스키마를 만들 수 있을까요?" → 계획을 올리기로 함.

## What Changes

- 모든 JSON 조회·쓰기 API에 Pydantic 응답 모델을 붙여 `/openapi.json`에 응답 칸, 형식, 빈 값 허용 여부를 공개한다.
- 서버는 응답을 보내기 전에 그 모델로 검사한다. 모양이 틀린 응답은 내보내지 않고 오류로 남긴다.
- 근거가 나가는 응답(판정, 보증값 후보, 손실 환산, 공학 검산, 일탈·질의 항목, 제안 포인트, 위험 조건 구성원)은 원문 위치를 모델에서 필수로 한다.
  판정·결과 값처럼 정해진 값만 쓰는 칸은 그 값 목록으로 제한한다.
- 화면 타입은 `/openapi.json`에서 만든다. CI가 다시 만들어 보고, 저장소의 것과 다르면 실패한다.
- 순서: 근거 API를 먼저 하고, 나머지 조회 API와 쓰기 API를 그다음에 한다(tasks.md 묶음 2 → 3·4).

## Non-Goals

- 요청 모델은 바꾸지 않는다(이미 Pydantic 모델이다).
- 응답 값 자체를 바꾸지 않는다. 칸 이름, 순서, 거르는 기준, 판정 계산은 그대로다. 화면이 쓰는 칸이 빠지면 안 된다.
- 화면에서 받은 JSON을 다시 검사하는 라이브러리(zod 등)는 넣지 않는다. 타입 생성과 서버 검사로 충분한지 먼저 본다.
- DB 스키마 변경 없음(마이그레이션 없음).
- 파일 내려받기 API(Word·엑셀)의 내용 형식은 이 change 범위가 아니다.

## Capabilities

### New Capabilities
- `api-contract`: API 응답 스키마 공개, 서버의 응답 검사, 근거 응답의 원문 위치 필수, 화면 타입과 서버 스키마 일치.

### Modified Capabilities
없음. `evidence-integrity`의 "근거 묶음"(위치가 없는 값은 내보내지 않음)은 그대로이고, 이 change는 그것을 응답 모양으로도 지키게 한다.

## Impact

- 백엔드: `api/schemas.py`(새 파일, 응답 모델), `api/runs.py`·`api/reference.py`의 `response_model`, `/openapi.json` 내보내기 명령.
- 프런트: `frontend/src/api.gen.ts`(만든 파일, 커밋함), `api.ts`의 손으로 쓴 타입을 만든 타입으로 바꿈. 어긋난 칸(`file_name` 등)은 화면을 고친다.
- 새 의존성 없음. 타입 생성은 `frontend/scripts/gen-api-types.mjs`(design.md 4).
- CI: 스키마 → 타입 다시 만들기 → 차이 검사 단계를 더한다.
- 위험: 지금 DB 값 중 모델과 맞지 않는 것이 있으면 그 API가 오류를 낸다. 구현 중 기존 테스트로 찾아 고친다(design.md 위험 1).
