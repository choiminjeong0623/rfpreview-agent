# Design

## 짝짓는 열쇠

`(정규화한 요구 원문, 정규화한 표 항목명, 정규화한 요구값 원문, 비교 제품)`. 정규화 = 공백 하나·앞뒤 공백 없음·소문자.
- 표 칸의 원문은 값만 있을 때가 많아("40 kA") 항목명과 요구값을 함께 쓴다.
- 비교 제품이 다르면 같은 요구라도 판정이 다르므로 제품도 넣는다(제품이 없는 판정은 NULL끼리).
- 글자가 조금만 달라도 뜻이 다를 수 있어 비슷한 문장 맞추기는 하지 않는다.

## 어떤 사람 판정인가

- 다른 검토(`run_id <> 지금`)의 지금 판정(`is_current`) 중 `review_status IN ('CONFIRMED','EDITED')`.
- 반려(REJECTED)는 "해당 없음"이라 힌트로 쓰지 않는다.
- 여럿이면 마지막 확정·수정 이력 시각이 가장 늦은 것(같으면 판정 번호 큰 것) → 같은 입력이면 같은 힌트(CR-11).
- 사유·사람·시각은 그 판정의 마지막 CONFIRM/EDIT 이력에서.

## 어디서 계산하나

`pipeline/review_memory.py`: 지금 검토의 판정 열쇠를 모으고, 다른 검토의 사람 판정 열쇠를 한 번에 읽어 dict로 맞춘다(DB 함수 정규화 대신 Python 정규화, 정답지 채점과 같은 `normalize`).
- `queries.run_judgments` 결과에 `past_decision`(없으면 null).
- 거르기 `past=differs`: 지금 검토 모든 판정의 힌트를 계산해 다른 줄 번호로 거른다(판정 수천 줄도 dict 비교라 가볍다).
- 칩 건수: `judgment_counts`에 `past_seen`, `past_differs`.

## 화면

- 판정 표 판정 칸 아래 작은 꼬리표 "지난 확정 일탈 후보"(같으면 회색, 다르면 주황 "지난 확정과 다름").
- 상세 패널 "지난 검토에서 사람이 본 판정" 줄: RV 번호 링크, 판정, 사람, 날짜, 사유.
- 판정 칩 줄에 "지난 확정과 다름 n"(0이면 숨김).

## 대안

- 판정 값에 바로 반영: CR-01(판정은 코드 규칙)·CR-08과 맞지 않는다.
- 표 하나(review_memory)에 미리 쌓기: 이력이 이미 있어 읽을 때 계산으로 충분하다. 마이그레이션 없음.

## 위험

- 같은 문장이 많지 않으면 힌트가 거의 없다(22개 RFP의 같은 문장 비율은 아직 안 잼). 실행 후 "지난 확정 n줄"로 효과를 본다.
