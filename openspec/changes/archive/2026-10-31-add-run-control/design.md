# Design

## 결정

- **취소 표시:** `review_run.cancel_requested_at`, `cancel_requested_by`(0018). 처리 흐름은 진행을 기록할 때(`_set_step`, 문서 처리 중 `report`)마다 이 칸을 읽어, 있으면 `RunCancelled`를 던진다. 문서 하나는 한 트랜잭션이라 멈춘 문서의 반쯤 만든 결과는 되돌려진다.
- **취소 뒤 단계:** 새 단계 값을 만들지 않고 FAILED + `failed_step` + 오류 문장 "○○이(가) 분석을 취소했습니다."로 둔다. 실행 요약에 `cancelled`(취소 요청이 있었고 FAILED)를 더해 화면이 문구를 고른다. 단계 값을 늘리면 목록·홈·사업 현황 분류(다른 담당 화면)를 모두 고쳐야 해서 뺐다.
- **멈춘 처리 정리:** 취소 요청 때 마지막 진행이 10분(화면 STALL_MS와 같은 값) 넘게 없으면 처리 흐름이 살아 있지 않다고 보고 바로 FAILED로 바꾼다(오류 문장 "진행이 멈춰 …").
- **다시 시도 입력:** 처리 시작 때 `graph_state.inputs`에 파일 경로와 사람이 정한 분류를 적는다. 올린 파일은 내용 해시 폴더에 남아 있으므로 같은 경로로 다시 돌린다. 이 change 전에 만든 검토나 파일이 지워진 검토는 409로 거절하고 다시 등록하라고 안내한다.
- **다시 시도 방식:** 같은 run_id로 흐름을 처음부터 다시 돌린다. 문서는 같은 처리 판·내용이면 다시 쓰고(NFR-05), 위험 조건·검산·보증값·손실·목록·제안·할 일은 단계마다 지우고 다시 만들며, 판정은 이전 줄을 is_current=false로 남긴다. 그래서 따로 "멈춘 단계부터"를 계산하지 않아도 끝난 문서는 AI를 다시 부르지 않는다. 실패·취소한 검토에는 사람 확인 기록이 없어 지울 것이 없다.
- **다시 시도 때 지우는 값:** 단계 FAILED → PROCESSING, `failed_step`, `error_message`, `finished_at`, 취소 요청 칸. `retry_count` + 1.
- **권한:** 로그인한 사용자 누구나(요청자 기록). 결재 권한과 무관한 처리 제어라서.

## 대안

- CANCELLED 단계 추가: 의미는 더 정확하지만 다른 담당 화면과 사업 현황 계산을 함께 고쳐야 한다. 동결 전 일정에 맞지 않아 뺐다.
- 멈춘 단계부터만 다시 돌리기: 단계별 상태 저장이 필요하고, 문서 재사용으로 이미 비용이 거의 같다.

## 위험

- 취소는 다음 진행 기록까지 걸린다. AI 한 묶음(수십 초)이나 단계 하나(일탈·질의 문장 쓰기)가 끝나야 멈출 수 있다.
- 10분 기준으로 멈춘 것으로 표시했는데 처리 흐름이 사실 살아 있으면, 그 흐름은 다음 진행 기록에서 취소를 보고 스스로 멈춘다(같은 FAILED).
- 다시 시도 중 이전 흐름이 아직 돌고 있으면 둘이 겹칠 수 있다. 다시 시도는 FAILED일 때만 받으므로, 위 10분 경우 말고는 겹치지 않는다.
