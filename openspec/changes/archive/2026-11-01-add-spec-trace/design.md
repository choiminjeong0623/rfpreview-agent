# Design

## 1. 무엇을 무엇과 잇나

| 고리 | 원본 | 잇는 방법 |
|---|---|---|
| FR | `docs/reference/기능요구사항명세서_v1.md` 1장 표(FR-01~17) | 표 줄을 읽는다 |
| FR → 스펙 | `docs/추적_연결.json` `fr.<FR>.specs` | capability 이름 목록(사람이 정함) |
| 스펙 → 시나리오 | `openspec/specs/<cap>/spec.md` `#### Scenario:` | 그대로 |
| FR → 화면 | `docs/추적_연결.json` `screens.<SCR>.fr` | 사람이 정함(README 번호표와 같게) |
| 화면 → 수용 기준 | `docs/screens/SCR-*.md` `**Given**` 줄 | 줄 끝 괄호 이름이 수용 기준 이름 |
| 화면 → 컴포넌트 | `docs/추적_연결.json` `screens.<SCR>.components` | 파일이 없으면 검사 실패 |
| 이름 → 테스트 | `backend/tests/*.py` docstring `Scenario: A / B — …`, `frontend/e2e/*.spec.ts` `test('이름'` | 이름이 글자 그대로 같으면 잇는다 |

연결 설정은 코드가 아닌 JSON 한 파일로 둬서 사람이 고치고 리뷰하기 쉽게 한다. 화면 주소·컴포넌트는 `App.tsx`에서 자동으로 뽑을 수도 있지만, 탭(SCR-08-x)처럼 주소가 없는 화면이 있어 사람이 정한다.

## 2. 생성기와 CI

`frontend/scripts/trace.mjs`(Node, 의존성 없음). `npm run trace`는 `docs/추적표.md`를 다시 쓰고, `npm run check:trace`는 다시 만든 내용이 파일과 다르면 실패한다(`check:api`와 같은 방식). 표에 날짜·시각을 넣지 않아 같은 입력이면 같은 파일이다.
실패 조건: 추적표가 낡음, 설정의 컴포넌트 파일 없음, 설정에 없는 FR·capability·SCR 이름, 이어진 시나리오·수용 기준이 하나도 없는 FR. 테스트 없는 시나리오는 실패시키지 않고 "검증 안 된 것"에 남긴다(지금 있는 빈곳을 한 번에 다 메울 수 없다).

## 3. 이름 맞추기

이름이 다른 테스트는 테스트 docstring·이름을 스펙 쪽 이름으로 고친다(스펙은 archive된 확정본이라 그대로). 한 테스트가 여러 시나리오를 볼 때는 `Scenario: A / B` 로 적는다. e2e 이름을 바꾸면 수용 기준 괄호도 같이 본다.

구현하며 정한 것:
- e2e 이름은 바꾸지 않는다(다른 화면 명세 괄호가 이미 그 이름을 쓴다). 대신 `test(` 바로 위 줄 `// Scenario: A / B`를 같은 테스트의 다른 이름으로 읽는다. 백엔드 docstring과 같은 "Scenario:" 표시라 규칙이 하나다.
- 도구 테스트(`scripts/*.test.mjs`, node --test)는 `test('Scenario: 이름')`으로 잇는다.
- 화면 명세 괄호에 "e2e `이름`"·"…, 백엔드 테스트"처럼 설명이 붙은 것은 테스트 이름만 남겼다.
- 테스트가 없는 9개는 억지로 잇지 않고 "검증 안 된 것"에 남긴다. 그중 SCR-08-1 "꼭 볼 것" 칩 3개, SCR-08-8 제출본 탭 인계 패키지 보기, SCR-07 메일·Teams 가져오기는 화면 명세(v4.96)에만 있고 **아직 만들지 않은 기능**이다. 추적표가 찾아낸 빈곳으로 남긴다.

## 4. 핵심 흐름 e2e

`e2e/core-flow.spec.ts` 한 테스트. 검토 등록 화면(SCR-07)에서 합성 데이터시트를 올려 분석 → 검토 상세에서 판정 하나 확정 → 결재 상신(엔지니어) → 결재 대기에서 승인(승인자) → 제출본 탭 인계 패키지 내려받기. 화면을 사람처럼 누르고, 각 단계 끝 상태를 본다. 이름 "RFP 한 건 처음부터 끝까지"를 FR-01·07·09·10 수용 기준으로 추적표에 잇는다.

## 5. 목업 배치 점검

`compare-mockup.mjs`를 v4.96 파일·26화면(새 화면 JudgeView·ProductView)으로 바꾼다. 나란히 찍기는 그대로 두고, 화면마다 "영역 표"를 더한다: 목업과 앱 DOM에서 정해 둔 영역 이름(`.ttl`, `.ais`, `.hc`, `.qsum`, `.pgtabs2`, `table` 등 목업 CSS 클래스. 앱이 목업 CSS 클래스를 그대로 쓰므로 같은 이름으로 찾는다)의 있음과 위→아래 순서를 비교한다. 결과는 `compare-out/layout.json`과 검수표 v4.96 장.
구현: 영역은 고정 목록 대신 "작업 영역 안에서 너비 30 % 넘고 높이 20px 넘는 블록의 첫 class"로 찾는다(화면마다 목록을 손으로 적지 않게). 앱 틀 class(`layout`, `main`)는 뺀다. 같은 class는 처음 나온 위치만 쓴다. 판정: 영역이 모두 있고 순서가 같으면 "배치 같음", 아니면 빠진·순서 다른 영역 이름과 `_공유.md` 차이 문서로 설명되는지.
대안: 픽셀 비교(pixelmatch) — 예시 값이 달라 거의 모든 화면이 "다름"이라 쓸모가 없어 택하지 않았다.

## 6. 위험

- 이름으로만 잇기 때문에 같은 이름의 다른 테스트가 잘못 이어질 수 있다. 시나리오 이름은 capability 안에서만 같으면 되므로, 추적표에는 이어진 테스트 파일을 같이 보여 사람이 확인하게 한다.
