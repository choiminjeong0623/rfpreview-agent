# Proposal

## Why

SDD의 뜻은 "스펙이 곧 검증 기준"이라는 데 있다. 지금은 명세서 FR → OpenSpec 시나리오 → 화면 명세 수용 기준 → 구현 → 테스트가 이름으로만 느슨하게 이어져 있다. 그래서 "이 요구사항이 어디에 구현되고 어떻게 검증됐는가"를 한눈에 보일 수 없고, 구현 뒤 스펙과 대조한 기록도 남지 않는다.
현황(2026-11-01): 화면 명세 수용 기준 160개 중 138개, OpenSpec 시나리오 605개 중 509개가 같은 이름의 테스트를 가진다. 나머지는 테스트가 없거나 이름이 다르다. 목업 대조 도구(`compare-mockup.mjs`)는 아직 v4.57 기준이다.
minjeong 11-01 "5단계: 스펙 기준으로 검증" 지시. 같은 날 "승인받지 않고 클로드의 제안대로 진행".

## What Changes

- 추적표 `docs/추적표.md`를 코드로 만든다: FR → OpenSpec capability(시나리오 수·테스트 있는 수) → 화면(SCR) → 구현 컴포넌트 → 테스트(백엔드·e2e 파일과 줄). 연결 설정은 `docs/추적_연결.json` 한 파일.
- 수용 기준·시나리오와 테스트는 이름으로 잇는다: 화면 수용 기준 끝 괄호 이름 = e2e `test()` 이름, 시나리오 이름 = 백엔드 테스트 docstring의 `Scenario:` 이름 또는 e2e 이름. 테스트가 없는 것은 표 끝 "검증 안 된 것"에 모인다.
- CI 프런트 작업에 `npm run check:trace`: 추적표가 지금 스펙·테스트와 다르거나, 연결 설정의 컴포넌트 파일이 없거나, 아무 수용 기준·시나리오와도 이어지지 않는 FR이 있으면 실패.
- 이름이 어긋난 테스트를 맞추고, 빠진 핵심 테스트를 더한다. 핵심 흐름 e2e 하나: 검토 등록 화면에서 올리기 → 분석 → 판정 확정 → 결재 상신 → 승인 → 인계 패키지.
- 목업 대조를 v4.96으로: 26개 화면을 나란히 찍고, 목업과 앱이 같이 쓰는 영역 이름(클래스)의 위아래 순서·있음을 코드로 비교한 "배치 점검"을 `docs/screens/검수표.md`에 남긴다.

## Non-Goals

- 픽셀 단위 같음 판정: 예시 값·글꼴·데이터 양이 달라 의미가 없다. 영역 순서·있음만 본다.
- CI에서 e2e·스크린샷 돌리기: 실행에 백엔드·DB·합성 문서가 필요하다. 지금처럼 로컬에서 돌리고 결과를 검수표에 남긴다.
- 기능 바꾸기: 화면·API 동작은 그대로. 마이그레이션 없음.
