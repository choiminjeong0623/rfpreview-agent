# Design

## 한꺼번에 확정

- API: `POST /runs/{run_id}/actions/bulk` 본문 `{ "target": "judgment", "ids": [..], "action": "CONFIRM", "actor_id": n }`. 응답 `{ "confirmed": n, "submission_check": … }`.
- 대상은 판정, 동작은 확정만 받는다. 수정·반려는 줄마다 사유가 달라 한 줄씩(`POST /actions`).
- 한 트랜잭션: 단계 확인 → 모든 id가 그 실행의 현재 판정인지 확인 → 줄마다 `_apply` + `log` → 보증값·목록·제안 포인트·전달을 한 번만 다시 만든다. 확인에 실패하면 아무것도 쓰지 않는다.
- 이미 확정된 줄도 다시 확정할 수 있다(지금 한 줄 확정과 같다). 화면은 확정하지 않은 줄만 보낸다.
- 다시 만들기를 한 번만 하는 이유: 한 줄 확정은 판정 결과를 바꾸지 않지만 지금 코드는 매번 목록·제안 포인트를 다시 만들고 언어 모델을 부른다. 45줄이면 45번.

## 보증값 요구값을 뺀 이유

- 처음에는 보증값 후보 응답에 요구값을 더하려 했다. 그런데 보증값 후보는 판정이 "보증값 작성"인 줄, 곧 요구값 칸이 빈 줄에서만 나온다.
  개발 DB 보증값 후보 662줄 모두 요구값·`table_row.required_raw`가 비어 있었다. 더해도 늘 빈 값이라 이 change에서 뺐다.
- 목업 데이터시트의 "고객 요구"는 판정 줄(`/judgments`의 `req_value_raw`)이다. 데이터시트 화면에서 판정과 보증값을 `requirement_id`로 합친다.

## 화면

- 목업 Detail `.bulk` 띠 두 가지와 표 왼쪽 고르기 칸(머리 칸은 보이는 줄 모두 고르기). 확정하면 목업과 같은 알림 "판정 n줄을 제안대로 확정했습니다."
- 담당자 확인 단계가 아니면(승인 대기·승인됨) 고르기 칸은 잠기고 띠는 숨긴다.
