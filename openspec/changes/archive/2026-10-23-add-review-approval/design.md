# Design

## Context

2·3단계가 만든 결과(요구사항, 위험 조건, 판정, 보증값, 손실 환산, 일탈·질의 목록, 제안 포인트)는 모두 "후보"다(CR-08). 이 change는 사람이 그 후보를 확인·승인하는 흐름(FR-10)과, 엔지니어·승인자가 결과를 보고 판단하는 화면을 만든다. 로그인은 범위 밖이라 사용자 구분은 `app_user.role`로만 한다.

## Goals / Non-Goals

- Goals: 멈춤 지점 2곳, 승인 기준 판단, 동작과 수정 이력, 채택한 제안 포인트만 전달, 화면.
- Non-Goals: 로그인·권한 관리, FR-11 담당자별 할 일(Should), 입찰 검토 요약 화면, 제출 파일 만들기(Word·Excel 양식 채우기).

## Decisions

- **멈춤 지점은 DB 단계로 둔다.** LangGraph 흐름은 처리 단계(documents → … → proposals)까지 돌고 `review_run.stage = ENGINEER_REVIEW`에서 끝난다(멈춤 1). 확인은 며칠 걸릴 수 있어 그래프를 메모리에 붙잡아 두지 않고, 단계(stage)와 `graph_state.step`이 체크포인트 역할을 한다. "담당자 확인 마치기"(`finish_review`)가 승인 기준을 판단해 `APPROVAL`(멈춤 2) 또는 `APPROVED`로 넘긴다. 승인자의 결정(`decide`)이 `APPROVED`/`REJECTED`로 끝낸다.
  - 대안: LangGraph interrupt + 체크포인터(Postgres). 상태를 두 곳(체크포인터, 결과 표)에 두게 되고 MVP에서 얻는 것이 없어 택하지 않았다.
- **걸린 기준이 없으면 바로 승인됨 [결정].** 승인 기준은 "하나라도 해당하면 승인자에게 간다"이므로, 아무 기준도 안 걸리면 승인 기록(`approval.decision = APPROVED`, 의견 "승인 기준에 해당 없음")을 남기고 승인됨으로 둔다.
- **승인 기준 판단 (코드만, CR-01).**
  - AR-01: 현재·반려하지 않은 판정 중 일탈 후보 1건 이상.
  - AR-02: "문제 없음"으로 닫지 않은 포괄 조항 1건 이상.
  - AR-03 [제안]: 확인 필요 비율 = (엔지니어가 아직 확인하지 않은 "확인 필요" 판정 + 빈 보증값 칸) ÷ (현재 판정 − 보증값 후보를 채운 칸) > `approval_rule.threshold`(0.20). 엔지니어가 확정·수정한 판정은 분자에서 빠진다.
  - AR-06: 닫지 않은 값 불일치 위험 조건 또는 빼지 않은 질의 항목이 남아 있음.
  - AR-07: 누락 점검에서 빠진 일탈이 있음.
  - AR-08: 전달할(채택·고쳐 채택) 제안 포인트가 있음 — 승인자가 전달 내용을 본다. 전달 대상은 언제나 채택한 것만이다.
- **동작과 상태.**

  | 대상 | 확정 | 수정 | 반려 / 버림 |
  |---|---|---|---|
  | 판정 | review_status CONFIRMED | 판정 값 바꿈, EDITED, 사유 문장 | REJECTED (목록·제안·보증값 대상에서 빠짐) |
  | 보증값 | CONFIRMED (빈 칸은 확정 불가) | 값·단위 넣음, 출처 ENGINEER, CONFIRMED | REJECTED |
  | 목록 항목 | CONFIRMED | 문장 바꿈, CONFIRMED | REMOVED (목록에서 빼기) |
  | 제안 포인트 | ADOPTED (채택) | 문장 바꿈, EDITED (고쳐 채택) | DISCARDED (버림) |
  | 위험 조건 | CONFIRMED | — | CLOSED_OK (문제 없음) |

  수정·반려·버림에는 사유가 필요하다. 동작은 담당자 확인 단계에서만 된다(비교 제품 바꾸기, 손실값 고치기도 같다).
- **수정 이력.** `review_log`에 대상 표·id, 동작, 이전 행, 새 행(JSON), 사유, 작업자, 시각을 남긴다. 비교 제품 바꾸기(`run_product_choice`), 손실값 고치기(`loss_calc`), 단계 이동(`review_run`)도 남긴다.
- **수정 뒤 다시 만들기.** 판정을 바꾸면 보증값·목록·제안 포인트를 다시 만들고 누락 점검을 다시 한다. 위험 조건을 바꾸면 목록과 제안 포인트를 다시 만든다. 다시 만들어도 사람의 확인 결과는 이어 쓴다: 목록 항목은 (종류, 묶음 키), 제안 포인트는 (종류, 요구사항, 근거 값), 보증값은 판정 id가 같으면 상태와 고친 문장·값을 그대로 둔다.
- **고친 문장의 숫자 검사.** 엔지니어가 고친 목록·제안 문장도 숫자를 원래 문장(근거 값으로 채운 문장)의 숫자와 대조해 다르면 숫자 불일치로 표시한다(CR-07을 사람 문장에도 경고로 적용). 팀 가정 제안 포인트는 고쳐도 "(팀 가정)"이 남는다(CR-06).
- **원문 위치는 그 실행의 문서만.** 같은 요구가 다른 실행의 문서에도 있으면(2단계 중복 묶기) 대표 요구사항에 그 위치도 붙어 있다. 결과 조회는 실행에 속한 문서의 위치만 낸다(E2E에서 발견해 고침).
- **화면.** React 한 페이지: 왼쪽에 검토 시작(올리기·서버 파일 고르기)과 실행 목록, 오른쪽에 실행 상태와 탭 9개(요구사항, 위험 조건, 적합성 판정, 보증값, 손실 환산, 일탈·질의 목록, 제안 포인트, 승인, 이력). 줄마다 원문 위치 칩을 누르면 원문이 열린다. 사용자 고르기로 엔지니어·승인자를 바꾼다(로그인 전 임시).
- **스키마(0005).** 판정 확인 상태(review_status), 보증값 상태 REJECTED·출처 ENGINEER, 목록·제안 문장 작성 주체 ENGINEER, 이력 색인, 기본 승인자.

## Risks / Trade-offs

- 로그인이 없어 누구나 사용자를 바꿀 수 있다. 승인자 확인은 역할만 본다 [확인 필요: 로그인 change].
- AR-03 기준(20 %)과 계산 방식은 [제안]이다. 실제 파일 1은 항목 사전에 없는 행이 많아 늘 걸린다.
- 반려된 실행은 "다시 확인하기"로 담당자 확인에 되돌려 고친 뒤 다시 올린다. 반려 전후의 승인 기록은 모두 남는다.
- 화면 E2E(Playwright)는 RFP 원문이 있어야 해서 CI에서는 돌리지 않는다. 합성 문서로 도는 백엔드 Scenario 테스트가 CI에서 확인한다.
