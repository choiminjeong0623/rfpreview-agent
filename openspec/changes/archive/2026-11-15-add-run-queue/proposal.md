# Proposal: 검토 실행 대기열 (add-run-queue)

## Why

11-14 코드 점검에서 찾은 문제 (등록 API가 웹 서버 안 `BackgroundTasks`로 분석을 바로 돌림):

- (가) 등록 요청 안에서 "판정할 문서가 있는가"를 보려고 모든 파일을 OCR까지 읽는다. 큰 스캔 PDF면 등록 응답이 몇 분 걸리고, 분석 때 같은 OCR을 한 번 더 한다.
- (나) 동시에 도는 분석 수에 상한이 없어 AI 요청 한도(429)와 DB 연결이 몰린다.
- (다) 분석이 웹 요청과 같은 스레드 풀을 나눠 쓴다.
- (라) OCR처럼 진행 기록 없이 긴 구간이 10분을 넘으면 "멈춤"으로 보이고, 이때 취소 → 다시 시도하면 취소 표시가 지워져 **같은 검토가 두 번 동시에 돈다**.
- (마) 서버를 다시 켜면 메모리 안 작업이 사라지는데 검토는 "처리 중"으로 남는다.
- (바) 등록 단추를 두 번 누르면 검토가 2개 생긴다.

관련: 명세서 v3 **FR-20**(Should), **NFR-11**(등록 응답), **NFR-12**(실행 하나), CR-11·12, FR-10 ④. 기존 capability `review-run`(처리 상태, 취소·다시 시도), `document-intake`(판정 대상 없는 등록 거절), `service-health`. 팀 프로젝트 뒤 개인 개선.

## What Changes

1. **DB 대기열** — 등록·다시 시도·문서 추가·단계부터 다시는 작업(`run_job`)만 넣고 응답한다. 처리기가 들어온 순서대로 `FOR UPDATE SKIP LOCKED`로 꺼낸다(새 서버 없음). 동시 실행 수 `RFP_RUN_WORKERS`(기본 2).
2. **처리기** — `rfp-worker` 명령(웹 서버와 다른 프로세스, docker compose `worker` 서비스). 처리기를 따로 띄우지 않는 개발·시험 환경은 `RFP_RUN_MODE=inline`(기본)으로 웹 서버가 같은 대기열 규칙(상한·토큰·살아 있음)으로 직접 꺼내 돌린다.
3. **실행 소유권** — 작업을 넣을 때마다 새 실행 토큰. 처리 흐름은 진행을 기록할 때마다 토큰을 보고, 잃었으면 결과를 쓰지 않고 멈춘다. 한 검토에 도는 실행은 하나(NFR-12).
4. **살아 있음과 정리** — 처리기가 30초마다 살아 있음을 적고, 3분 넘게 끊긴 작업은 다시 넣는다(최대 2번, 저장된 흐름 상태로 멈춘 단계부터). 넘으면 "처리 실패 — 처리기가 멈춤". 화면의 멈춤 판단도 살아 있음으로.
5. **등록은 받기만** — 판정 대상 검사는 미리 보기 결과(같은 파일 해시)를 다시 쓰고, 없으면 docx는 OCR 없이, PDF는 첫 쪽 글자 층만 본다(NFR-11).
6. **중복 등록 방지와 업로드 상한** — 요청 키(10분), 파일 하나 100 MB·요청 하나 300 MB.
7. **화면·상태 점검** — 검토 목록·머리글 진행 표시에 "대기 중 n번째", `/api/health`에 실행 방식·살아 있는 처리기 수·대기 작업 수.

## Non-Goals

- Redis·Celery 같은 새 대기열 서버.
- 처리기 여러 대에 걸친 우선순위·공정 분배(들어온 순서만).
- 대기열 관리 화면.
