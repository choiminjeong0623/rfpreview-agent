# Design

## 결정

1. **같은 검토를 처음부터 다시 돌린다.** 문서 추가는 `review_run.graph_state.inputs`(처음 파일·분류)에 새 파일을 더해 실행 흐름 전체를 다시 돌린다. 다시 시도(`prepare_retry`)와 같은 길이다. 처리한 문서는 처리 열쇠(내용 해시 + 분류 + 코드판)로 다시 쓰여 AI를 부르지 않고 `requirement_id`·`value_id`가 그대로다. 대안(새 문서만 처리하고 판정만 더하기)은 문서 간 값 불일치·쌍 후보·목록을 따로 맞춰야 해 버렸다.
2. **같은 줄 = (requirement_id, value_id, product_code, compare_rule_id).** 판정 단계 전에 지금 판정 줄(is_current)을 기억하고, `judge_run` 뒤 새 줄과 이 열쇠로 맞춘다(NULL도 같음으로 봄). 확정·반려는 상태만, 수정은 판정 값·사유·여유까지 옮긴다. 비교 제품이 바뀌면(추가 문서 때문에 제품 선택이 바뀜) 다른 줄로 보고 후보로 둔다(CR-08).
3. **보증값은 판정 줄을 다시 잇는다.** `warranty_candidate.judgment_id`를 새 줄로 바꾸면 `build_warranty`가 판정 줄 기준으로 확정·반려한 후보를 그대로 둔다.
4. **위험 조건은 새로 만든 뒤 바꾼다.** 이전 위험 조건을 먼저 지우면 `output_item_source`가 막는다(다 끝난 검토를 다시 돌리면 실패하던 원인). 새로 저장하고, 같은 열쇠(종류·표현 id·항목·요구사항 묶음)의 상태·목록 출처·묶음 열쇠(`("QUERY","R",risk_id)`)를 옮긴 뒤 이전 것을 지운다. 같은 열쇠면 AI 설명과 근거 문장(`claim_evidence`)도 새 위험 조건으로 옮겨 AI를 다시 부르지 않는다.
5. **이어받기는 늘 한다.** 판정·위험 조건 단계가 매번 이어받는다. 사람이 손대지 않은 검토는 할 일이 없고, 문서 추가가 중간에 실패해 다시 시도해도 같은 규칙이 적용된다.
6. **엔지니어만, 담당자 확인 단계에서만.** 승인자·협조 부서는 403, 다른 단계는 409. 같은 파일 이름은 409(정정본은 이름을 바꿔 올림).
7. **이력**: `review_log(target_table='run_document', target_id=run_id, action='ADD', after_value={"files": [...]})`. 0021에서 동작 값에 ADD를 더한다.

## 위험

- 수정 이력 줄은 이전 판정 번호를 가리킨다. 이력 탭은 실행 단위라 그대로 보이지만, 새 판정 줄에서 이전 이력을 따라가지는 않는다.
- 검산(FR-12) 기반 질의 문장은 묶음 열쇠가 검산 번호라 다시 쓰일 수 있다(문장 재사용만 안 될 뿐 확인 상태는 목록 단계 규칙을 따른다).
- 큰 RFP는 다시 분석에 시간이 걸린다. 처리한 문서는 다시 쓰므로 더한 문서 처리 시간 + 판정 뒤 단계 시간이다.
