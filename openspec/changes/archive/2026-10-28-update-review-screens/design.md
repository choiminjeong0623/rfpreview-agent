# Design

## Context

검토 상세(`views/ReviewDetail.tsx`)는 머리글만 목업대로 바뀌었고 본문은 예전 탭(`Findings`, `Compliance`, `Outputs`, `Approval`)을 `.legacy` 범위 안에서 그대로 쓴다.
목업 Detail 화면의 CSS는 `src/mockup/Detail.css`로 이미 들어와 있다(`usePageCss('Detail')`). 판정 목록 API는 판정 값·설비 묶음으로만 거르고 판정 번호 순으로 준다.

## Decisions

### 1. 화면 하나씩, 묶음 하나씩
- 이 change는 화면이 많아 `tasks.md`의 `## N.` 묶음마다 로컬 브랜치 `feat/update-review-screens-<N>`를 쌓는다. archive는 마지막 묶음에서 한다.
- 묶음 1: 검토 상세 요약 칸·탭 틀 + 판정 탭(SCR-08, SCR-08-1). 다른 탭은 묶음마다 하나씩 목업대로 바꾸고, 그전까지 탭 안에 예전 화면을 둔다.

### 2. 판정 목록 API
- `GET /judgments`에 `type_code`(주 유형), `q`(대소문자 무시, 항목 이름·영문 항목명·원문 표 이름에 들어감), `unconfirmed=true`(review_status = CANDIDATE), `order=priority`를 더한다. 기본값은 지금과 같다.
- 판정 순서는 SQL `CASE result` 순서 + judgment_id. 반려한 판정(review_status REJECTED)은 거르지 않는다(지금도 보임).
- `GET /judgment-counts`: `{by_result: {RESULT: n}, total, unconfirmed, unconfirmed_comply}`. 칩 6개를 요청 한 번으로 채운다.
- 대안: 화면이 판정 값마다 `limit=1`로 5번 불러 X-Total-Count를 읽기 → 요청이 많고 "확정 안 한 줄만"과 함께 쓰면 10번이 된다.

### 3. 화면 구성
- 탭은 화면 안 상태로 고르고 주소는 바꾸지 않는다(SCR-00: `#/reviews/:id`, 탭은 화면 안에서 고름). 처음 탭은 판정.
- 요약 칸 값: 일탈·질의·작성 필요는 `judgment-counts`, 확인 필요 비율은 `approval.review_ratio`(AR-03과 같은 계산), 손실 환산은 `losses` 합(값 없는 줄이 있으면 "—").
- 판정 표 행 값: 항목 = 한글 항목 이름(없으면 영문), 아래 줄 = 영문 항목명. 요구값 = 원문 값 + 단위. 제품값 = 제품 값 + 단위, 아래 줄 = 제품 코드. 원문 위치 = 첫 위치(`locationText`), 더 있으면 "외 n곳".
- 상세 패널의 원문 문장은 `GET /requirements/{id}`의 `text_raw`, 목록 문장은 `GET /outputs`에서 그 판정을 출처로 가진 항목. 판정 바꾸기·확정은 지금 `POST /actions`(judgment EDIT·CONFIRM).
- 판정 표는 한 쪽 10줄(목업), 아래 `Pager`.

### 4. 예시 탭
- 상업 조건, 지난 RFP 비교, 제출본 탭은 `_공통규칙.md` 5장대로 예시 띠 + `src/examples/`의 예시 데이터. 저장 단추를 두지 않는다.

## Risks / Trade-offs

- 검색어 `q`는 ILIKE라 판정이 수천 줄이면 느릴 수 있다. 지금 실행은 판정 수백 줄이라 받아들인다.
- 예전 탭 화면은 묶음마다 하나씩 지우므로 중간 묶음에는 목업 탭 안에 예전 화면이 섞여 보인다.

## 묶음 3에서 발견한 것

- 판정 탭 머리 단추·손실값 저장처럼 동작이 빨리 이어지면 `DetailBody`의 다시 불러오기 신호가 한 번만 올라 화면이 옛 값에 머물렀다. 신호를 함수형 갱신으로 바꾸고, `useLoad`는 늦게 온 앞선 응답을 버린다.
- 문서 목록(document_catalog)에서 같은 번호로 잡히는 서로 다른 파일을 같은 규칙 판으로 처리하면 `ux_document_version`(file_no, processing_key) 중복으로 실행이 실패한다. 이 change 범위 밖이라 고치지 않고, e2e 손실 환산 문서는 번호 94를 따로 쓴다. [확인 필요]

## 묶음 7: 문서 읽기 점검

- 점검 줄은 저장하지 않고 요청할 때마다 처리 결과에서 코드로 만든다. 사람이 확인한 기록만 `read_check`(실행 + 점검 키)에 남긴다. 키는 원천 id로 만들어 같은 문서를 다시 쓰는 실행에서도 바뀌지 않는다 (CR-11).
- 그림은 지금까지 버리던 정보라 `doc_figure`를 새로 둔다. 문서 처리 코드가 바뀌어 처리 판(`code_version`)이 바뀌므로 다음 실행부터 문서를 다시 처리한다.
- 되돌리기도 이력에 남기려고 review_log 동작에 `UNDO`를 더했다 (마이그레이션 0011).
- 미확인 점검은 승인 기준(AR)이 아니다. 승인 화면 정보에 `read_unchecked`로만 넣고, 상신 전 확인 목록에 주의 줄로 보인다. 상신을 막지 않는다.
- [확인 필요] 실제 RFP에서 머리글 없는 표 줄이 너무 많으면 거르는 규칙을 정한다 (`docs/screens/SCR-08-2_공유.md`).

## 묶음 8: 협조 요청 현황 (SCR-13)

- 요청 항목은 FR-11 할 일(`assignment`)을 그대로 쓴다. 부서 탭마다 `GET /assignments?role=`로 모든 검토의 요청을 모은다. 검토 번호·파일 이름·보낸 사람(검토 담당)을 같은 쿼리에 붙인다.
- 화면 상태는 할 일 상태에서 코드로 정한다: 할 일 → 미확인(보낸 지 24시간 넘으면 "24시간 넘게 미확인"), 하는 중·끝 → 확인. 새 상태 칸을 만들지 않는다.
- 받는 사람 화면은 목업에 없어, 받는 역할 사용자가 같은 상세 창에서 확인함·처리 끝을 누른다. 예전 "내 할 일" 화면은 지운다.
- 재요청·회신 글·직접 요청·내보내기는 API를 만들지 않는다(대안: 상태 칸 추가 — 범위가 커서 뒤로 미룸). 요청하기는 예시 창.

## 묶음 9: 홈 (SCR-03)

- 새 API 없이 `GET /runs`, `GET /assignments?role=`(세 부서), `GET /users`로 만든다. 카드 열은 검토 단계에서 코드로 정하고, 담당자 확인 단계라도 미확인 협조 요청이 남으면 "협조 대기"로 둔다(목업의 협조 대기 단계는 저장된 단계가 아니다).
- 팀 업무는 사용자마다 지금 하는 일을 역할로 정한다: 엔지니어는 마감이 가장 가까운 진행 중 검토, 승인자는 결재 대기 수, 담당자는 미확인 협조 요청 수. 접속 상태는 없다.
- 공지·시스템 공지·자료실·행사는 게시판 API가 없어 예시 영역. 판정 기준 변경 알림은 제품표·규칙 변경 추적이 생긴 뒤 만든다.
