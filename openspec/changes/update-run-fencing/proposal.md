# Proposal: 실행 소유권을 저장 순간에 확인 (update-run-fencing)

## Why

`add-run-queue`(0042)는 작업을 넣을 때마다 새 실행 토큰을 검토에 적고, 처리 흐름은 진행을 기록할 때마다 `check_cancel`로 토큰이 아직 자기 것인지 본다. 그런데 이 확인은 **읽고 비교만** 한다. 확인한 뒤 같은 트랜잭션에서 판정·위험 조건 같은 단계 결과를 쓰고 커밋하기까지의 사이에 다른 연결이 작업을 다시 넣어 토큰을 바꾸면, 밀려난 옛 실행의 결과가 그대로 저장된다.

`docs/08-known-limits.md`는 이 빈틈을 "대기열 소유권 확인은 '확인한 뒤 쓰기'"로 적어 두었고, 다음 단계로 "단계 결과를 쓰는 문장마다 토큰 조건을 붙이기(펜싱)"를 남겼다. 마지막 결과(담당자 확인·실패) 저장만 토큰 조건이 붙은 한 문장이라 안전하다.

이 프로젝트가 내세우는 "안정적인 비동기 처리"(NFR-12: 한 검토에 도는 실행은 언제나 하나)를 테스트로 증명하려면 이 빈틈부터 닫아야 한다. 2026-11-22 포트폴리오 점검 P0 계획의 1-2번이다.

관련: 명세서 v3 **NFR-12**, FR-20, CR-11. 기존 capability `review-run`의 "실행 소유권".

## What Changes

1. **저장 순간 확인(펜싱)** — 처리 흐름의 연결이 커밋할 때마다, 같은 트랜잭션 안에서 검토 행을 잠가(`SELECT … FOR UPDATE`) 토큰을 다시 읽고, 자기 토큰이 아니면 그 트랜잭션을 되돌리고 멈춘다(`RunSuperseded`). 단계 노드의 커밋뿐 아니라 단계 안에서 부르는 함수(목록·손실 환산·문장 벡터 등)의 커밋과 문서 병렬 처리 연결의 커밋도 같은 규칙을 따른다.
2. **순서는 DB가 정함** — 작업 넣기(`enqueue`)와 다시 넣기(`reclaim`)는 이미 같은 검토 행을 `UPDATE`로 잠그므로, 옛 실행의 커밋과 새 토큰 쓰기 중 먼저 잠근 쪽이 이기고 다른 쪽은 기다린다. 옛 실행이 먼저면 그 결과는 저장된 뒤 새 실행이 같은 줄 이어받기로 바꾸고, 새 토큰이 먼저면 옛 결과는 저장되지 않는다.
3. **테스트로 증명** — 단계 한가운데(토큰 확인 뒤, 커밋 전)에 다른 연결로 작업을 다시 넣는 동시성 테스트. 고치기 전 코드에서 실패하는 것을 먼저 보이고, 고친 뒤 옛 실행의 그 단계 결과가 0건인지 본다.
4. **문서** — `docs/08-known-limits.md`의 해당 줄을 "해결됨"으로, `docs/03` ADR에 결정 한 줄.

## Non-Goals

- 처리기 살아 있음 판단(30초·3분) 바꾸기. AI 응답을 기다리는 동안 살아 있는 것으로 보이는 점은 그대로 둔다.
- LangGraph 흐름 상태(checkpoint) 저장 방식 바꾸기. 흐름 상태는 별도 연결에 저장되며, 노드가 커밋에서 멈추면 그 노드의 흐름 상태는 남지 않는다(design.md 위험).
- 화면·API 응답 바꾸기. 마이그레이션 없음.

## Capabilities

### Modified Capabilities

- `review-run`: "실행 소유권" 요구사항에 저장 순간 확인과 시나리오 "단계 저장 직전에 밀려남"을 더한다.

## Impact

- 백엔드: `pipeline/run.py`(실행 연결의 커밋), `pipeline/run_queue.py`(잠금 순서 주석), `pipeline/graph_flow.py`(`open_like`), `pipeline/service.py`(실행 연결 열기).
- 테스트: `tests/test_run_queue.py`.
- 문서: `docs/08-known-limits.md`, `docs/03-adr.md`.
- 마이그레이션·API·화면 바뀜 없음.
